Chapter 8: Database Concepts

Based on NCERT's Class XII Computer Science textbook. Why do we need a database at all, instead of just files? This chapter walks through a school attendance example to expose file system limitations — redundancy, inconsistency, isolation, dependence — then builds up the relational data model: relations, attributes, tuples, domain, degree, cardinality, and the four kinds of keys that hold a relational database together.

Chapter 8 of 13 NCERT pp. 111–130 ~3 Hours Exercise Included

By the end of this chapter, you'll be able to

  • List the six limitations of a plain file system and explain each with an example
  • Identify attribute, tuple, domain, degree and cardinality in a given relation
  • Pick out candidate, primary, composite primary and foreign keys in a schema

8.1 Introduction

A school keeping attendance on paper — 'P'/'A' against each roll number, every working day — faces real problems at scale: re-entering student details each year, inconsistent names, lost/damaged registers, and manual calculation errors. The fix is to store STUDENT details and ATTENDANCE separately on a computerised system — but first through plain files, which turn out to have their own problems.

8.2 File System & Its Limitations

A file is a container for data on a storage device. Our school example needs two files — STUDENT (RollNumber, SName, SDateofBirth, GName, GPhone, GAddress) and ATTENDANCE (AttendanceDate, RollNumber, SName, AttendanceStatus). As the number of files and data volume grows, six limitations surface:

  • (A) Difficulty in Access — files provide no retrieval mechanism of their own; every access path needs a hand-written application program.
  • (B) Data Redundancy — the same data duplicated across files/rows (SName appears in both files; two siblings' guardian details repeat).
  • (C) Data Inconsistency — redundant copies that fall out of sync (a name corrected in one file but not the other).
  • (D) Data Isolation — related files (STUDENT, ATTENDANCE) have no built-in link/mapping between them.
  • (E) Data Dependence — change a file's structure, and every program reading it must be updated too.
  • (F) Controlled Data Sharing — hard to enforce "guardians can view but not edit attendance" style access rules at the file level.

8.3 Database Management System

A Database Management System (DBMS) is software to create and manage databases — letting users store, update, modify and retrieve data, acting as the interface between the database and end users/application programs. Examples: MySQL, Oracle, PostgreSQL, SQL Server, Microsoft Access, MongoDB. Retrieving data through special commands is called querying.

8.3.1 File System → DBMS

Converting the school's two files into a database means:

  1. Drop SName from ATTENDANCE — it's already in STUDENT, linked via the common field RollNumber.
  2. Split guardian details into their own GUARDIAN table, so each guardian's data is stored only once (not once per sibling).
  3. Add a GUID (Guardian ID) column — unique per guardian, since names alone can't distinguish two people, and even phone numbers can change.
Three related tables
STUDENT(RollNumber, SName, SDateofBirth, GUID)
GUARDIAN(GUID, GName, GPhone, GAddress)
ATTENDANCE(AttendanceDate, RollNumber, AttendanceStatus)

8.3.2 Key Concepts in DBMS

  • Database Schema — the design: table names, columns, data types, constraints, relationships.
  • Data Constraint — a restriction on what a column can hold, e.g. NOT NULL + UNIQUE on RollNumber.
  • Meta-data / Data Dictionary — the schema plus constraints, stored in the database catalog; "data about the data."
  • Database Instance — the snapshot of actual data at a given moment (empty right after schema creation, then populated).
  • Query — a request for information, written in SQL (Chapter 9).
  • Data Manipulation — Insertion, Deletion, Update of records.
  • Database Engine — the underlying programs a DBMS uses to create the database and handle queries.
DBMS has costs too

Textbook caveat: shifting from files to a DBMS means buying hardware/software, training users on querying, and recurring backup/recovery costs — and centralising data increases vulnerability, since a single hardware/software failure can halt operations for everyone.

8.4 Relational Data Model

The most common data model. In the relational model, tables are called relations. Each row corresponds to a real-world entity (a student, a guardian); each column interprets what that data means.

Relational terminology
ATTRIBUTE    a column/field -- e.g. GUID, GName, GPhone, GAddress
TUPLE        a row -- one related set of n values
DOMAIN       the set of allowed values for an attribute (usually = its data type)
DEGREE       the NUMBER OF ATTRIBUTES (columns) in a relation
CARDINALITY  the NUMBER OF TUPLES (rows) in a relation

GUARDIAN relation: 4 attributes, 5 tuples
  → Degree = 4, Cardinality = 5

8.4.1 Three Properties of a Relation

What makes a relation different from a plain table
Property 1 (attributes):
  - each attribute name is unique within the relation
  - attribute order doesn't matter

Property 2 (tuples):
  - every tuple is distinct -- no two rows identical across ALL attributes
  - tuple order doesn't matter

Property 3 (values):
  - all values in one attribute come from the same domain/data type
  - every value is atomic (not further divisible, e.g. one 10-digit phone number)
  - an attribute holds ONE value per tuple, never multiple
  - NULL represents an unknown/non-applicable value

8.5 Keys in a Relational Database

Every tuple must be distinguishable from every other — keys enforce that and link relations together.

8.5.1 Candidate Key

Any attribute (or attribute set) whose values are always unique — a candidate for primary key. In GUARDIAN, both GUID and GPhone are candidate keys (no two guardians share either).

8.5.2 Primary Key

The candidate key the database designer actually picks to uniquely identify tuples. The remaining candidate key(s) become alternate keys — e.g. with GUID chosen as primary key, GPhone becomes the alternate key.

8.5.3 Composite Primary Key

When no single attribute is unique enough alone, two or more are combined. In ATTENDANCE, neither RollNumber alone (repeats across dates) nor AttendanceDate alone (repeats across students) works — but {RollNumber, AttendanceDate} together is always unique, since a student is marked only once per working day.

8.5.4 Foreign Key

An attribute in one relation (the referencing/foreign relation) whose values are drawn from the primary key of another relation (the primary/master relation) — this is what links tables together. A foreign key can be NULL if it isn't itself part of its own table's primary key.

STUDENTATTENDANCE schema with keys (underline = primary key)
STUDENT(   RollNumber, SName, SDateofBirth, GUID )
                                                 \
GUARDIAN(  GUID, GName, GPhone, GAddress )  <----'  -- GUID in STUDENT is a
                                                        foreign key referencing
                                                        GUARDIAN's primary key

ATTENDANCE( AttendanceDate, RollNumber, AttendanceStatus )
                             \
STUDENT(    RollNumber, ... ) <--'  -- RollNumber in ATTENDANCE is a foreign
                                       key referencing STUDENT's primary key

-- ATTENDANCE's own primary key is the COMPOSITE {AttendanceDate, RollNumber}

6. Exercise (from the textbook)

NCERT Exercise, Chapter 8

Work through these on paper

  1. Give the term for each: (a) collection of logically related records, (b) a DBMS file describing the data stored in the database, (c) an attribute that can uniquely identify tuples, (d) the special value for an unknown attribute, (e) an attribute that can uniquely identify tuples but isn't the chosen primary key, (f) software used to create/manipulate/maintain a relational database.
  2. Why are foreign keys allowed to hold NULL? Give an example.
  3. Differentiate: (a) database state vs. database schema, (b) primary key vs. foreign key, (c) degree vs. cardinality of a relation.
  4. Compared to a file system, how does a DBMS avoid data redundancy?
  5. What file-system limitations does a relational DBMS overcome?
  6. A sports preference table has roll_no 17 listed twice (Badminton and Football), and a row with roll_no NULL for Kabaddi. (a) Can roll_no 24's preference legitimately be NULL? (b) Which relational property does roll_no 17's duplicate entry violate — what key/constraint would catch it? (c) Can the NULL-roll_no Kabaddi row exist in this relation?
  7. Two sections each keep a sports-preference table with different row/column order. Are the two relation states equivalent? Justify.
  8. Design a canteen database: (a) what relation/attributes store each item + price (each only once — what constraint enforces that)? (b) should purchase quantity go in a new relation or the existing one — name the attributes, primary key and foreign key so a bill can't duplicate and can only reference available items. (c) where should "calories" live?
  9. For EMPLOYEE(AadharNumber, Name, Address, Department, EmployeeID) and DEPENDENT(EmployeeID, DependentName, Relationship): (a) which EMPLOYEE attributes could be candidate keys? (b) which tables/key retrieve a given employee's dependents? (c) what's the degree of each relation?
  10. Given a SCHOOL_UNIFORM database with UNIFORM(UCode PK, UName NOT NULL, UColor) and COST(UCode, Size, Price >0) composite PK: can you insert (a) (7, Handkerchief, NULL), (4, Ribbon, Red), (8, NULL, White) into UNIFORM? (b) (7, S, 0), (9, XL, 100) into COST? Justify each.
  11. For MOVIE(Movie_ID, MovieName, ReleaseDate) and AUDI(AudiNo, Movie_ID, Seats, ScreenType, TicketPrice) where one movie can show in multiple auditoriums: (a) is Movie_ID alone a correct primary key? (b) is AudiNo alone correct for AUDI? (c) is there a foreign key here?
  12. For a STUDENT-PROJECT database with STUDENT(RollNo, Name, Class, Section, Registration_ID), PROJECT(ProjectNo, PName, SubmissionDate), PROJECT_ASSIGNED(Registration_ID, ProjectNo): (a) name each table's primary key, (b) find the foreign key(s) in PROJECT_ASSIGNED, (c) is there an alternate key in STUDENT, (d) can RollNo repeat?
  13. For the same database, can you: (a) insert a student with a missing roll number, (b) insert a student with a missing registration number, (c) insert a project without a submission date, (d) insert (IP-101-19, 206) into PROJECT_ASSIGNED?
