Week 5: Knowledge Representation, Logic & Planning

Search finds paths; logic lets an agent know things and derive new facts from them. This week covers how knowledge is represented and reasoned over — from propositional logic and expert systems to knowledge graphs — and how an agent turns that knowledge into a plan of actions.

Phase 2 of 6 Week 5 of 19 ~3–4 Hours Hands-on Exercise Included

By the end of this week, you'll be able to

  • Represent facts and rules in propositional and first-order logic
  • Perform inference with forward chaining, backward chaining and resolution
  • Describe planning problems in STRIPS and solve them with search

1. Propositional Logic & Inference

Propositional logic builds sentences from true/false symbols with ¬ (not), ∧ (and), ∨ (or), ⇒ (implies) and ⇔ (iff). A knowledge base (KB) is a set of sentences assumed true. A sentence α is entailed (KB ⊨ α) if α is true in every world where the KB is true.

model_checking.py
from itertools import product

# KB: Rain => WetGrass,  Sprinkler => WetGrass,  not WetGrass
symbols = ["Rain", "Sprinkler", "WetGrass"]

def kb(m):
    return ((not m["Rain"] or m["WetGrass"]) and
            (not m["Sprinkler"] or m["WetGrass"]) and
            not m["WetGrass"])

def entails(kb, query):
    for values in product([True, False], repeat=len(symbols)):
        m = dict(zip(symbols, values))
        if kb(m) and not query(m):
            return False          # a world where KB holds but query fails
    return True

print(entails(kb, lambda m: not m["Rain"]))   # True: it didn't rain

Checking every model costs 2n for n symbols. Resolution is a single inference rule that is complete for propositional logic: convert the KB and the negated query to clauses, and repeatedly resolve pairs; deriving the empty clause proves the query. Modern SAT solvers use this idea and routinely handle millions of variables.

2. First-Order Logic

Propositional logic can't say "every student who passes all courses graduates" without writing one symbol per student. First-order logic adds objects, predicates, functions and quantifiers (∀ for all, ∃ there exists).

first-order sentences
∀x  Student(x) ∧ PassedAll(x) ⇒ Graduates(x)
∀x  Parent(x, y) ∧ Parent(y, z) ⇒ Grandparent(x, z)
∃x  Course(x) ∧ Teaches(Ada, x)
Student(Ravi)   PassedAll(Ravi)

From these, an inference engine derives Graduates(Ravi) by unification — finding the substitution {x/Ravi} that makes the rule's premises match the known facts. Logic programming languages like Prolog are built on exactly this mechanism.

3. Rule-Based Systems & Knowledge Graphs

Forward chaining starts from known facts and fires rules until nothing new can be derived — data-driven. Backward chaining starts from a goal and works back to facts that would prove it — goal-driven, the strategy behind Prolog and diagnostic expert systems.

forward_chaining.py
rules = [
    ({"fever", "cough"}, "flu_suspected"),
    ({"flu_suspected", "short_of_breath"}, "refer_to_doctor"),
    ({"rash", "fever"}, "measles_suspected"),
]

def forward_chain(facts):
    facts = set(facts)
    changed = True
    while changed:
        changed = False
        for premises, conclusion in rules:
            if premises <= facts and conclusion not in facts:
                facts.add(conclusion)
                changed = True
    return facts

print(forward_chain({"fever", "cough", "short_of_breath"}))

Knowledge graphs represent knowledge as subject–predicate–object triples — (Bengaluru, capitalOf, Karnataka) — and power search engines' fact panels and product recommendations. They complement LLMs: an LLM can fluently produce text, while a knowledge graph provides verifiable facts it can retrieve (the idea behind the retrieval-augmented generation week later in this tutorial).

Why expert systems faded — and what survived

Hand-writing thousands of rules was expensive and brittle when situations fell outside them. But rule engines are still everywhere where decisions must be auditable: tax calculations, insurance underwriting, access control and compliance checks.

4. Classical Planning with STRIPS

Planning finds a sequence of actions to reach a goal, like search, but describes states as sets of logical facts and actions by their preconditions and effects. This factored representation lets planners use general-purpose heuristics instead of problem-specific ones.

strips_planner.py
from collections import deque

# Blocks world: action = (name, preconditions, add list, delete list)
def actions(blocks):
    for a in blocks:
        for b in blocks:
            if a != b:
                yield (f"stack({a},{b})",
                       {f"clear({a})", f"clear({b})", f"onTable({a})"},
                       {f"on({a},{b})"},
                       {f"clear({b})", f"onTable({a})"})
                yield (f"unstack({a},{b})",
                       {f"on({a},{b})", f"clear({a})"},
                       {f"onTable({a})", f"clear({b})"},
                       {f"on({a},{b})"})

def plan(start, goal, blocks):
    frontier, seen = deque([(frozenset(start), [])]), {frozenset(start)}
    while frontier:
        state, steps = frontier.popleft()
        if goal <= state:
            return steps
        for name, pre, add, delete in actions(blocks):
            if pre <= state:
                nxt = frozenset((state - delete) | add)
                if nxt not in seen:
                    seen.add(nxt)
                    frontier.append((nxt, steps + [name]))

start = {"onTable(A)", "on(B,A)", "clear(B)", "onTable(C)", "clear(C)"}
goal = {"on(A,B)", "on(B,C)"}
print(plan(start, goal, ["A", "B", "C"]))

Real planners describe domains in PDDL (Planning Domain Definition Language) and use heuristics such as "ignore delete lists", a relaxation exactly like those from Week 2. LLM agents that break a task into steps are doing informal planning; the classical formulation remains useful for checking that a proposed plan's preconditions are actually met.

5. Hands-on Exercise

Hands-on

A diagnostic expert system and a planner

  1. Write 12–15 rules for diagnosing why a laptop won't connect to Wi-Fi (e.g. airplane mode, driver, router, password).
  2. Implement forward chaining to derive all conclusions from a set of symptoms, and backward chaining to test one hypothesis, printing the chain of rules used as an explanation.
  3. Extend the STRIPS planner to handle 4 blocks, and add a heuristic (number of goal facts not yet satisfied) so you can use A* from Week 2. Compare nodes expanded with BFS.
Hint

For explanations, store the rule that produced each derived fact. Following those links backwards from the conclusion gives a human-readable "why" — the feature that made expert systems trusted in medicine and finance.

6. Knowledge Check

4 quick questions. Expand each to check your answer.

Q1

What does KB ⊨ α (entailment) mean?

In every possible world where all sentences of the knowledge base are true, α is also true. It's the formal notion of "α follows from what we know".

Q2

What can first-order logic express that propositional logic cannot conveniently express?

General statements about objects and relations using variables and quantifiers, like "every parent of a parent is a grandparent", without writing a separate symbol for every individual.

Q3

When would you choose backward chaining over forward chaining?

When you have a specific goal to prove and many facts and rules, most of which are irrelevant to it. Backward chaining only explores rules that could help prove the goal; forward chaining derives everything.

Q4

What are the three parts of a STRIPS action?

Preconditions (facts that must hold to apply it), an add list (facts it makes true) and a delete list (facts it makes false).
