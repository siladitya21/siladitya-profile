Week 32: WebRTC & Peer-to-Peer Communication

Week 27 covered the server pushing data to a client. WebRTC solves a different problem entirely: two browsers exchanging audio, video, or data directly with each other, with the server only ever brokering the initial handshake.

1. WebRTC vs. Server-Mediated Real-Time

Week 27 drew a line between SSE, WebSockets and polling — all three route data through your server. WebRTC is a different category: once two browsers have exchanged enough information to find each other, media and data flow directly between them, without your server touching every frame.

  • SSE / WebSockets (Week 27) — every message passes through your backend. Simple to reason about, easy to log and moderate, but your server pays the bandwidth cost of every byte.
  • WebRTC — your server (via a small piece called a signaling service, Section 4) helps two peers agree on how to connect, then gets out of the way. Audio, video and arbitrary data all travel peer-to-peer. Lower latency, no server bandwidth bill for the media itself — at the cost of needing to solve NAT traversal (Section 5), something a server-mediated connection never has to think about.

The deciding question: does this feature need the server to see or process every message (chat moderation, a shared database record), or is the server's only real job introducing two parties who then talk directly (a video call, a P2P file transfer, a multiplayer game's position updates)? WebRTC is for the second case.

2. Capturing Camera & Mic

navigator.mediaDevices.getUserMedia() is promise-based and asks the user for permission the first time it's called — wrap it in an injectable service so every consumer gets a signal instead of juggling the raw promise and manually handling permission-denied errors.

media-capture.service.ts
import { Injectable, signal } from '@angular/core';

export type MediaStatus = 'idle' | 'requesting' | 'granted' | 'denied';

@Injectable({ providedIn: 'root' })
export class MediaCaptureService {
  private readonly _localStream = signal<MediaStream | null>(null);
  private readonly _status = signal<MediaStatus>('idle');

  readonly localStream = this._localStream.asReadonly();
  readonly status = this._status.asReadonly();

  async startCapture(): Promise<void> {
    this._status.set('requesting');
    try {
      const stream = await navigator.mediaDevices.getUserMedia({
        video: { width: 640, height: 480 },
        audio: true,
      });
      this._localStream.set(stream);
      this._status.set('granted');
    } catch {
      // NotAllowedError (permission denied) or NotFoundError (no camera/mic) both land here
      this._status.set('denied');
    }
  }

  stopCapture(): void {
    this._localStream()?.getTracks().forEach((track) => track.stop());
    this._localStream.set(null);
    this._status.set('idle');
  }
}

track.stop() is the detail easiest to forget — just discarding the MediaStream reference doesn't turn off the camera's recording light; each individual track has to be stopped explicitly. Section 3 covers wiring this into the component lifecycle so it always happens.

binding a stream to a <video> element — call-preview.ts
import { Component, inject, effect, viewChild, ElementRef } from '@angular/core';
import { MediaCaptureService } from './media-capture.service';

@Component({
  selector: 'app-call-preview',
  template: `<video #localVideo autoplay muted playsinline></video>`,
})
export class CallPreview {
  private media = inject(MediaCaptureService);
  private videoRef = viewChild.required<ElementRef<HTMLVideoElement>>('localVideo');

  constructor() {
    effect(() => {
      const stream = this.media.localStream();
      const video = this.videoRef().nativeElement;
      video.srcObject = stream; // not a signal-bound attribute -- MediaStream needs the DOM property directly
    });
  }
}

srcObject has to be set imperatively on the element — it isn't something Angular's template binding syntax handles, so an effect() that reacts to the stream signal and reaches into the DOM directly is the correct, idiomatic way to connect the two.

3. RTCPeerConnection, Offer/Answer & ICE

RTCPeerConnection is the object that actually represents one peer-to-peer link. Setting it up always follows the same shape, called the offer/answer exchange:

  1. Caller creates an RTCPeerConnection, adds its local tracks, and calls createOffer() — a blob of SDP (Session Description Protocol) text describing what it can send/receive.
  2. Caller sends that offer to the callee through the signaling service (Section 4) — RTCPeerConnection has no network transport of its own for this step.
  3. Callee sets the offer as its remote description, creates an answer, and sends that back the same way.
  4. Both sides exchange ICE candidates as they're discovered — each one is a possible network path (a local IP, a public IP learned from STUN, Section 5) the browser could use to actually reach the other peer.
peer-call.service.ts (caller side)
import { Injectable, signal, inject, DestroyRef } from '@angular/core';
import { SignalingService } from './signaling.service';

const ICE_SERVERS: RTCConfiguration = {
  iceServers: [{ urls: 'stun:stun.l.google.com:19302' }], // Section 5
};

@Injectable({ providedIn: 'root' })
export class PeerCallService {
  private signaling = inject(SignalingService);
  private destroyRef = inject(DestroyRef);
  private pc: RTCPeerConnection | null = null;

  readonly remoteStream = signal<MediaStream | null>(null);
  readonly connectionState = signal<RTCPeerConnectionState>('new');

  async startCall(localStream: MediaStream): Promise<void> {
    this.pc = new RTCPeerConnection(ICE_SERVERS);

    localStream.getTracks().forEach((track) => this.pc!.addTrack(track, localStream));

    this.pc.ontrack = (event) => this.remoteStream.set(event.streams[0]);
    this.pc.onconnectionstatechange = () => this.connectionState.set(this.pc!.connectionState);
    this.pc.onicecandidate = (event) => {
      if (event.candidate) this.signaling.sendIceCandidate(event.candidate);
    };

    const offer = await this.pc.createOffer();
    await this.pc.setLocalDescription(offer);
    this.signaling.sendOffer(offer);

    this.destroyRef.onDestroy(() => this.hangUp());
  }

  async handleAnswer(answer: RTCSessionDescriptionInit): Promise<void> {
    await this.pc?.setRemoteDescription(answer);
  }

  async handleRemoteIceCandidate(candidate: RTCIceCandidateInit): Promise<void> {
    await this.pc?.addIceCandidate(candidate);
  }

  hangUp(): void {
    this.pc?.getSenders().forEach((sender) => sender.track?.stop());
    this.pc?.close();
    this.pc = null;
    this.remoteStream.set(null);
  }
}

destroyRef.onDestroy(() => this.hangUp()) is the cleanup habit this whole week depends on — an open RTCPeerConnection left behind when a component is destroyed keeps the camera/mic active and the connection alive indefinitely. Wiring teardown through DestroyRef (not a manual ngOnDestroy, since this is an injectable service, not a component) guarantees it runs whenever the thing that started the call goes away.

4. A Signaling Service

"Signaling" is just the unglamorous job of relaying offers, answers and ICE candidates between two peers before RTCPeerConnection can take over. Nothing in the WebRTC spec defines how signaling has to work — it only assumes some channel exists.

Week 27's EventSource won't work here: SSE is one-directional, and signaling needs both peers to send and receive. A plain WebSocket, relayed through a small backend room, is the standard choice:

signaling.service.ts
import { Injectable, signal } from '@angular/core';

type SignalMessage =
  | { type: 'offer'; sdp: RTCSessionDescriptionInit }
  | { type: 'answer'; sdp: RTCSessionDescriptionInit }
  | { type: 'ice-candidate'; candidate: RTCIceCandidateInit };

@Injectable({ providedIn: 'root' })
export class SignalingService {
  private socket: WebSocket | null = null;
  readonly incoming = signal<SignalMessage | null>(null);

  connect(roomId: string): void {
    this.socket = new WebSocket(`wss://api.example.com/signaling/${roomId}`);
    this.socket.onmessage = (event) => {
      this.incoming.set(JSON.parse(event.data) as SignalMessage);
    };
  }

  sendOffer(sdp: RTCSessionDescriptionInit): void {
    this.socket?.send(JSON.stringify({ type: 'offer', sdp } satisfies SignalMessage));
  }

  sendIceCandidate(candidate: RTCIceCandidate): void {
    this.socket?.send(
      JSON.stringify({ type: 'ice-candidate', candidate: candidate.toJSON() } satisfies SignalMessage)
    );
  }

  disconnect(): void {
    this.socket?.close();
    this.socket = null;
  }
}

The signaling server itself (the backend "room" the WebSocket connects to) is deliberately out of scope for an Angular course — the point here is the client-side contract: a channel that can carry three small JSON message shapes before the real, peer-to-peer connection takes over.

5. STUN, TURN & NAT Traversal

Almost every device sits behind a NAT (home routers, mobile carriers, corporate networks) — a device's local IP (192.168.x.x) isn't reachable from outside its own network. ICE candidate gathering (Section 3) exists specifically to find a path around this.

  • STUN (Session Traversal Utilities for NAT) — a lightweight public server a browser briefly contacts to ask "what's my public IP and port, from the outside?" That becomes one more ICE candidate. STUN is enough for most home/consumer NATs, and it's free — stun.l.google.com:19302 is a commonly used public one.
  • TURN (Traversal Using Relays around NAT) — for symmetric NATs and strict corporate firewalls where no direct path can be found at all, TURN is a relay server that both peers connect to, and it forwards traffic between them. It solves connectivity, but at the cost of the exact server-bandwidth bill WebRTC otherwise avoids (Section 1) — and running one reliably means paying for a TURN provider or hosting coturn yourself.
a production ICE server list
const ICE_SERVERS: RTCConfiguration = {
  iceServers: [
    { urls: 'stun:stun.l.google.com:19302' },
    {
      urls: 'turn:turn.example.com:3478',
      username: 'generated-per-session',
      credential: 'generated-per-session',
    },
  ],
};

In practice, list both: the browser's ICE agent tries every candidate (direct, STUN-discovered, TURN-relayed) and automatically picks the best one that actually works for this specific pair of networks. A demo on one Wi-Fi network will often connect on STUN alone; the same code against a strict corporate network may fall back to TURN — this is exactly why both should always be configured in anything beyond a local demo.

6. RTCDataChannel

The same peer connection that carries audio/video can also carry arbitrary data — no media required at all. A RTCDataChannel behaves much like a WebSocket, but the bytes travel peer-to-peer, same as the media tracks in Section 3.

adding a data channel — peer-call.service.ts extension
// Caller side: create the channel before the offer
const channel = this.pc.createDataChannel('chat');
channel.onopen = () => console.log('data channel open');
channel.onmessage = (event) => this.incomingMessage.set(event.data);

// Callee side: the channel arrives as an event instead of being created
this.pc.ondatachannel = (event) => {
  event.channel.onmessage = (e) => this.incomingMessage.set(e.data);
};

// Either side, once open:
channel.send(JSON.stringify({ text: 'hello', at: Date.now() }));

A data channel is useful even in an otherwise audio/video-only call — cursor positions in a collaborative tool, chat alongside a video call, or game state in a multiplayer prototype all fit naturally here, without standing up a separate WebSocket connection for a feature the existing peer connection can already carry.

7. Testing a Call End-to-End with Playwright

Week 19's Playwright coverage carries over directly, but getUserMedia() adds one new problem: a CI runner has no camera or microphone, and a real browser will either hang on a permission prompt or reject the call outright. Chromium (and therefore Playwright) solves this with two launch flags built for exactly this case.

playwright.config.ts
import { defineConfig } from '@playwright/test';

export default defineConfig({
  use: {
    launchOptions: {
      args: [
        '--use-fake-device-for-media-stream', // synthesizes a moving-pattern video + tone audio
        '--use-fake-ui-for-media-stream',      // auto-grants the camera/mic permission prompt
      ],
    },
  },
});

With both flags set, getUserMedia() resolves with a real (synthetic) MediaStream instead of hanging — the app under test behaves exactly as it would with a genuine camera, which is what makes an actual end-to-end call test possible instead of mocking WebRTC away entirely.

A call needs two peers, so the test needs two independent browser contexts — each with its own cookies, storage and (via the config above) its own fake camera — standing in for two different users:

webrtc-call.spec.ts
import { test, expect } from '@playwright/test';

test('two peers connect and exchange a chat message', async ({ browser }) => {
  const callerContext = await browser.newContext();
  const calleeContext = await browser.newContext();
  const caller = await callerContext.newPage();
  const callee = await calleeContext.newPage();

  const roomId = 'e2e-test-room';
  await caller.goto(`/call/${roomId}`);
  await callee.goto(`/call/${roomId}`);

  await caller.getByRole('button', { name: 'Start Call' }).click();

  // PeerCallService's connectionState signal (Section 3) renders as a data attribute --
  // polling it via Playwright's auto-retrying expect() is simpler than hooking page-internal state.
  await expect(caller.locator('[data-connection-state]')).toHaveAttribute(
    'data-connection-state',
    'connected'
  );
  await expect(callee.locator('[data-connection-state]')).toHaveAttribute(
    'data-connection-state',
    'connected'
  );

  // Both

toHaveJSProperty('readyState', 4) is the detail worth noting — it reads a live property off the actual DOM element (HAVE_ENOUGH_DATA on an HTMLVideoElement), rather than asserting on something Angular rendered once and forgot about. That's the real payoff of testing WebRTC this way: the assertion confirms media is genuinely flowing between two browser processes, not just that two signals happened to update.

8. Hands-on Exercise

Hands-on

Build a two-peer video call with a text side-channel

Two browser tabs (or two devices on the same network) calling each other directly.

Requirements:

  1. Build MediaCaptureService (Section 2) and a call-preview component that shows your own camera before a call starts.
  2. Build SignalingService (Section 4) against any WebSocket relay — a minimal Node.js room server that just re-broadcasts whatever it receives to the other socket in the same room is enough; the backend logic itself isn't the point of this exercise.
  3. Build PeerCallService (Section 3) wiring offer/answer and ICE candidate exchange through the signaling service, with both STUN and (if you have access to one) a TURN server configured.
  4. Add a RTCDataChannel (Section 6) carrying a simple text chat alongside the video.
  5. Open two browser tabs, join the same "room," and confirm video, audio and chat all work end to end.
  6. Close one tab mid-call and confirm (via connectionState) that the other side detects the disconnect, and that your own camera's recording light turns off when you hang up.
Hint

Test on the same Wi-Fi network first — it will very likely connect on STUN alone, which tells you nothing about whether your TURN config actually works. To genuinely exercise TURN, test between two networks you know are strict (e.g. your home network and a phone on cellular data with Wi-Fi off), or temporarily force it by removing the STUN entry from iceServers.

9. Knowledge Check

Five quick questions. Expand each to check your answer.

Q1

Why can't Week 27's EventSource/SSE pattern be reused as a WebRTC signaling channel?

SSE is one-directional — the server can push to the client, but the client can't send messages back over the same connection. Signaling needs both peers to send offers/answers/ICE candidates and receive them, so it needs a bidirectional channel like a WebSocket.

Q2

What's the practical difference between a STUN server and a TURN server?

STUN only helps a peer discover its own public IP/port so the other side has a candidate to try — the two peers still connect directly. TURN is a relay: when no direct path exists (symmetric NAT, strict firewalls), all traffic is forwarded through the TURN server itself, which costs real bandwidth on that server, unlike a successful STUN-based connection.

Q3

In PeerCallService (Section 3), why does hangUp() call sender.track?.stop() instead of just calling pc.close()?

Closing the RTCPeerConnection ends the call, but it doesn't release the underlying camera/mic tracks captured back in Section 2 — those keep running (and the recording light stays on) until each track's own .stop() is called. Both steps are needed for a genuinely clean hang-up.

Q4

A multiplayer prototype needs to send frequent cursor-position updates between two connected users. Per Section 6, should this go over a new WebSocket or the existing RTCDataChannel?

If a peer connection already exists between the two users (for audio/video, or even just as the signaling-negotiated link), a data channel over it reuses that existing peer-to-peer path instead of standing up a second, server-mediated WebSocket connection for data the two peers can already exchange directly.

Q5

Without --use-fake-device-for-media-stream and --use-fake-ui-for-media-stream (Section 7), what actually happens when a Playwright test calls getUserMedia() in CI?

A CI runner has no real camera or microphone, and a headless browser can't click a native permission prompt — so the call either rejects (no device found) or hangs waiting on a permission dialog nothing will ever answer. The two flags remove both problems: one auto-grants the permission prompt, the other substitutes a synthetic video/audio stream, so getUserMedia() resolves the same way it would with real hardware.
