Week 3: Time, Clocks & Ordering Events

On one machine, "which happened first?" has an easy answer. Across machines it doesn't, because every machine has its own clock and none of them agree exactly. This week covers why physical clocks can't be trusted to order events, then builds the logical alternatives — Lamport clocks and vector clocks — that capture causality without needing synchronized time at all, and finishes with how modern databases combine both.

By the end of this week, you'll be able to

  • Explain why wall-clock timestamps from different machines can't safely order events
  • Define the happens-before relation and implement Lamport clocks
  • Implement vector clocks and use them to detect concurrent events

1. Physical Clocks Drift

Every computer keeps time with a quartz crystal oscillator, and no two crystals tick at exactly the same rate. Drift depends on temperature and manufacturing; a figure often quoted for server hardware is up to around 200 parts per million. Even a smaller drift adds up quickly:

how fast clocks diverge — python
seconds_per_day = 24 * 60 * 60   # 86,400

for ppm in (20, 50, 200):
    drift = ppm / 1_000_000 * seconds_per_day
    print(f"{ppm:>3} ppm  ->  {drift:.1f} s per day")

#  20 ppm  ->  1.7 s per day
#  50 ppm  ->  4.3 s per day
# 200 ppm  ->  17.3 s per day

Machines correct this with the Network Time Protocol (NTP), periodically asking a time server and adjusting. But NTP's accuracy is limited by the very network delays from Week 2: over the public internet it's typically within milliseconds to tens of milliseconds, and much worse if the network is congested or the NTP server is misconfigured. Clocks can also jump: NTP may step a clock backwards, and leap seconds have caused real outages when software assumed time only moves forward.

2. Wall-Clock vs. Monotonic Time

Operating systems expose two different clocks, and mixing them up is a classic bug:

the two clocks — python
import time

time.time()       # WALL CLOCK: seconds since 1970-01-01 UTC
                  # - comparable across machines (roughly)
                  # - can JUMP backwards or forwards when NTP corrects it
                  # - use for: timestamps shown to humans, log dates

time.monotonic()  # MONOTONIC CLOCK: seconds since some arbitrary point
                  # - never goes backwards
                  # - meaningless across machines or after reboot
                  # - use for: measuring durations, timeouts, rate limits

start = time.monotonic()
do_work()
elapsed = time.monotonic() - start   # correct even if NTP adjusts the clock

The deeper problem is using wall-clock timestamps from different machines to decide which event came first. A common strategy, last write wins (LWW), keeps whichever write has the largest timestamp. With skewed clocks, it silently throws away data:

last-write-wins losing a write it shouldn't
 Node A's clock is 300 ms AHEAD.  Node B's clock is correct.

 real time  event
 10:00:00.000  client writes x = 1 via node A  -> stamped 10:00:00.300
 10:00:00.100  client reads x = 1, then writes x = 2 via node B
                                               -> stamped 10:00:00.100

 LWW compares stamps: .300 > .100, so x = 1 "wins".
 The later write (x = 2) is silently discarded — no error, no log.
Timestamps from different clocks do not order events

If correctness depends on which of two events on different machines came first, wall-clock timestamps alone are not enough. LWW is acceptable only where losing a concurrent write is harmless (caches, "last seen" fields) — not for anything a user would notice going missing.

3. The Happens-Before Relation

In 1978, Leslie Lamport's paper "Time, Clocks, and the Ordering of Events in a Distributed System" reframed the question. We often don't need to know when things happened in real time — only whether one event could have influenced another. He defined the happens-before relation, written a → b:

  • If a and b happen on the same process and a comes first, then a → b.
  • If a is sending a message and b is receiving that same message, then a → b.
  • If a → b and b → c, then a → c (transitivity).

If neither a → b nor b → a, the events are concurrent (written a ∥ b): neither could have known about the other. Concurrent doesn't mean "at the same instant" — it means causally independent.

three processes exchanging messages
 P1:  a ───────── b(send m1) ────────────────────── e
                     \
 P2:  c ──────────── d(recv m1) ── f(send m2)
                                      \
 P3:  g ─────────────────────────────── h(recv m2)

 a → b → d → f → h     (a chain of causality across three processes)
 c → d                 (same process)
 a ∥ c,  e ∥ f,  g ∥ b  (no message path connects them)

4. Lamport Clocks

A Lamport clock is a single counter per process that assigns every event a number consistent with happens-before. The rules are short:

lamport clock — python
class LamportClock:
    def __init__(self):
        self.time = 0

    def tick(self) -> int:
        """Call for every local event, including before sending."""
        self.time += 1
        return self.time

    def send(self) -> int:
        return self.tick()            # attach this value to the message

    def receive(self, msg_time: int) -> int:
        self.time = max(self.time, msg_time) + 1
        return self.time

The guarantee: if a → b, then L(a) < L(b). The converse is not true. L(a) < L(b) does not tell you that a caused b; they may be concurrent. Lamport clocks can't detect concurrency.

What they can give you is a total order every node agrees on: sort events by (lamport_time, node_id), breaking ties by node ID. That order respects causality, which is enough for things like a fair mutual-exclusion queue or for deciding which of two operations to apply first in a replicated log.

Why the max() matters

On receive, jumping to max(local, received) + 1 is what pulls a lagging process forward. It ensures anything it does next is numbered after everything the sender knew about, which is exactly the happens-before guarantee.

5. Vector Clocks: Detecting Concurrency

To tell whether two events are causally related or concurrent, each process keeps a vector with one counter per process: "how many events from each process do I know about?"

vector clock — python
class VectorClock:
    def __init__(self, node: str, nodes: list[str]):
        self.node = node
        self.v = {n: 0 for n in nodes}

    def tick(self) -> dict:
        self.v[self.node] += 1
        return dict(self.v)

    def send(self) -> dict:
        return self.tick()                       # attach a copy to the message

    def receive(self, other: dict) -> dict:
        for n, t in other.items():               # element-wise max...
            self.v[n] = max(self.v[n], t)
        return self.tick()                       # ...then count the receive

def happened_before(a: dict, b: dict) -> bool:
    return all(a[n] <= b[n] for n in a) and a != b

def concurrent(a: dict, b: dict) -> bool:
    return not happened_before(a, b) and not happened_before(b, a)
comparing two vector timestamps
 a = {P1: 2, P2: 0, P3: 0}
 b = {P1: 2, P2: 1, P3: 0}   every entry >= a's, and not equal -> a → b

 c = {P1: 3, P2: 0, P3: 0}
 d = {P1: 2, P2: 1, P3: 0}   c is ahead on P1, d is ahead on P2  -> c ∥ d

Vector clocks give the full answer: a → b if and only if V(a) < V(b). Replicated databases use the same idea under the name version vectors: when two replicas hold versions of a key whose vectors are concurrent, the system knows it has a genuine conflict to resolve (Weeks 6 and 13) rather than an old version to discard.

The cost: one entry per participant

A vector clock grows with the number of processes. That's fine for a handful of replicas, but awkward with thousands of clients. Real systems bound it, for example by tracking only server replicas rather than every client.

6. Best of Both: Hybrid Logical Clocks & TrueTime

Logical clocks capture causality but have nothing to do with real time, so you can't ask "what was the state at 10:00?" Modern databases combine the two approaches:

  • Hybrid Logical Clocks (HLC), used by CockroachDB and others, store a physical timestamp plus a small logical counter. They stay close to wall-clock time, which makes them human-meaningful and good for snapshot reads, while still guaranteeing that if a → b then HLC(a) < HLC(b), even when clocks are skewed.
  • TrueTime, from Google's Spanner database, uses GPS receivers and atomic clocks in every datacenter. It returns an interval [earliest, latest] that is guaranteed to contain the true time. Spanner then waits out the uncertainty ("commit wait") before making a write visible, so timestamp order matches real-time order globally.
The pattern to remember

When you can't eliminate clock uncertainty, make it explicit and bounded, then design around the bound. TrueTime spends hardware to keep the interval small (a few milliseconds). Systems without that hardware use HLC and accept a larger uncertainty window.

8. Knowledge Check

5 quick questions. Expand each to check your answer.

Q1

Why should you measure a timeout or request duration with a monotonic clock rather than the wall clock?

The wall clock can jump backwards or forwards when NTP corrects it, so a duration computed from wall-clock readings can be negative or wildly wrong. A monotonic clock never goes backwards, so differences between its readings are reliable durations on that machine.

Q2

Lamport timestamps show L(a) = 3 and L(b) = 7. What can you conclude about events a and b?

Only that b did not happen before a. Either a → b, or the two are concurrent. Lamport clocks guarantee that a → b implies L(a) < L(b), but the reverse doesn't hold, so they can't distinguish causality from concurrency.

Q3

Given vector timestamps x = {A:3, B:1} and y = {A:2, B:4}, how are x and y related?

They are concurrent. x is ahead on A (3 > 2) while y is ahead on B (4 > 1), so neither vector is less than or equal to the other in every component. Neither event could have known about the other.

Q4

Describe how last-write-wins with wall-clock timestamps can silently lose a write.

If the node that accepted an earlier write has a clock running ahead, that write can get a larger timestamp than a later write accepted by a node with an accurate clock. LWW keeps the larger timestamp, so the causally later write is discarded with no error.

Q5

What problem does Spanner's "commit wait" solve, and what does it rely on?

It makes timestamp order match real-time order across the globe. TrueTime returns a bounded uncertainty interval for the current time, using GPS and atomic clocks. Spanner waits until the commit timestamp is guaranteed to be in the past everywhere before making the write visible, so any transaction that starts later is guaranteed a larger timestamp.
