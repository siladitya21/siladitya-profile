Week 7: Partitioning & Consistent Hashing

Replication (Weeks 5–6) puts copies of all your data on multiple machines; it doesn't help once the data itself no longer fits on one. Partitioning (also called sharding) splits a dataset across machines so each holds only a slice of it. This week covers the two ways to split — by range and by hash — why naive hashing makes every rebalance move almost everything, how consistent hashing fixes that, and what has to change about indexes and request routing once data lives on more than one node.

Module 2 of 5 Week 7 of 16 ~3 Hours Hands-on Exercise Included

By the end of this week, you'll be able to

  • Compare range and hash partitioning, and explain how each can create a hot spot
  • Explain why naive mod-N hashing causes a near-total reshuffle when a node joins or leaves
  • Implement consistent hashing with virtual nodes and reason about its rebalancing cost
  • Describe how secondary indexes and request routing work across partitions

1. Why Partition at All

Replication keeps copies of the same data on multiple machines; it doesn't shrink the data. Two limits eventually force a dataset to be split across machines instead:

  • It no longer fits: a table with billions of rows outgrows a single node's disk (and its memory for caching).
  • It no longer fits through one door: a single leader can only absorb so many writes per second, no matter how fast its disk is.

Partitioning (also called sharding) splits a dataset into pieces — partitions — so each node holds only a slice of it. Partitioning and replication compose: a real cluster usually partitions the data and replicates each partition, so "partition 3" might live as a leader on node A with followers on nodes B and C, while "partition 7" has its leader on node D.

partitioning + replication together
              PARTITION 1              PARTITION 2
            (keys A-M, say)          (keys N-Z, say)
         leader: node A           leader: node D
         followers: B, C          followers: E, F

Each node stores ONE partition's full replica set, not a slice of every
partition. Losing node A loses nothing — B or C still has partition 1.

2. Range vs. Hash Partitioning, and Hot Spots

The core decision is how a key maps to a partition.

Range partitioning assigns each partition a contiguous range of keys (sorted, like A–M and N–Z). It keeps keys in sorted order within and across partitions, which makes range scans ("all orders from March") fast and cheap. The risk is a hot spot: if keys are monotonically increasing (timestamps, auto-increment IDs), every new write lands in the same "latest" partition while the others sit idle.

Hash partitioning assigns a key to a partition based on hash(key) mod N (or, better, consistent hashing — Section 3). A good hash function spreads keys uniformly, so writes land roughly evenly across partitions regardless of key order. The cost: sorted range scans across keys now have to query every partition, since consecutive keys are scattered by design. A hash-partitioned system can still hot-spot if one specific key is extremely popular ("celebrity key") — hashing fixes an ordering problem, not a popularity one.

range vs. hash — same keys, different partitions
RANGE (sorted by key)              HASH (sorted by hash(key))
P1: user_0001 .. user_3333         P1: user_0042, user_2918, user_7701, ...
P2: user_3334 .. user_6666         P2: user_0019, user_4450, user_9123, ...
P3: user_6667 .. user_9999         P3: user_0007, user_3301, user_8844, ...

range scan "users 1000-2000"       range scan "users 1000-2000"
  → touches only P1                  → must touch P1, P2 AND P3
A common fix for both: a composite key

Many systems partition by a hash of part of the key (e.g. user_id) but keep a second part sorted within the partition (e.g. timestamp). Writes spread evenly across users, while a range scan for one user's events stays fast within their partition.

3. Consistent Hashing & Virtual Nodes

Naive hash partitioning computes hash(key) mod N for N nodes. The problem shows up the moment N changes: adding one node changes the modulus for every key, so almost every key maps to a different node, even though only one node joined.

why mod-N hashing reshuffles everything
N=4:  hash(key) % 4   maps key "x" (hash=13) to node 13 % 4 = 1
N=5:  hash(key) % 5   maps the SAME key to node       13 % 5 = 3

Changing N from 4 to 5 changes the result for most keys, not just the
ones that should logically move to the new node.

Consistent hashing fixes this by hashing both keys and nodes onto the same ring (imagine hash values 0 to 2³²-1 arranged in a circle). A key belongs to the first node found walking clockwise from the key's position. Adding a node only takes over the arc between it and the previous node clockwise — every other key's owner is unchanged.

consistent hash ring lookup — python-style pseudocode
import bisect

class HashRing:
    def __init__(self):
        self.ring = []           # sorted list of (hash_position, node)

    def add_node(self, node, virtual_nodes=100):
        for i in range(virtual_nodes):
            pos = hash(f"{node}-{i}")
            bisect.insort(self.ring, (pos, node))

    def get_node(self, key):
        pos = hash(key)
        idx = bisect.bisect(self.ring, (pos, None)) % len(self.ring)
        return self.ring[idx][1]            # first node clockwise from pos

The virtual_nodes parameter is virtual nodes (vnodes): each physical node claims many small, scattered arcs instead of one big one. Without vnodes, a few unlucky large arcs leave some nodes overloaded and others idle, and a newly joined node takes over one potentially huge arc all at once. With a few hundred vnodes per physical node, load evens out statistically, and both joining and leaving redistribute many small arcs instead of one large one — smoother, and spread across more of the cluster.

4. Rebalancing & Secondary Indexes

Rebalancing is the act of actually moving data when partitions are added, removed, or resized. A good rebalancing strategy moves only the data that logically needs to move (which consistent hashing minimizes), keeps the affected partitions available for reads and writes throughout the move, and is triggered automatically rather than needing a human to compute new assignments by hand.

Partitioning also complicates secondary indexes — indexes on a field other than the partition key (e.g. "find all orders with status=shipped" when orders are partitioned by order_id). Two approaches:

  • Document-partitioned (local) index: each partition indexes only its own documents. A query on the secondary field must fan out to every partition and merge results ("scatter-gather") — writes stay local and fast, reads get more expensive.
  • Term-partitioned (global) index: the index itself is partitioned by the indexed field, so a query hits only the relevant index partition(s) — reads stay cheap, but a single write may now need to update an index partition on a different node, often asynchronously.
Global indexes are usually eventually consistent

Keeping a global secondary index perfectly in sync with every write would need a distributed transaction (Week 12) on every write. Most systems that offer global indexes (DynamoDB's global secondary indexes, for example) instead update them asynchronously, so a query against one can briefly lag behind the latest write.

5. Request Routing

Once data is spread across partitions that move over time, a client (or the node it first contacts) needs to know which node currently owns a given key. Three common approaches:

  • Client-side routing: the client embeds the partitioning logic (e.g. the same hash ring) and talks directly to the right node, refreshing its view of the cluster periodically. Lowest latency, but every client must stay in sync with cluster changes.
  • Routing tier / coordinator: clients always talk to any node (or a dedicated proxy), which forwards the request to the correct owner. Simpler clients, one extra network hop.
  • Gossip-based membership: nodes exchange cluster state with each other in the background (Cassandra's approach), so any node a client reaches can answer "who owns this key" without a separate coordination service.

All three need a source of truth for "which node owns which partition right now," especially during a rebalance. Many systems externalize that into a dedicated coordination service — exactly the ZooKeeper/etcd role previewed in Week 11 and built properly once consensus (Weeks 9–10) is available.

6. Hands-on Exercise

Hands-on

Measure the rebalancing cost of mod-N hashing vs. a consistent hash ring

Quantify the problem from Section 3 instead of just reading about it.

Part 1 — Baseline the naive approach:

  1. Generate 100,000 random keys. Assign each to a node using hash(key) % N for N=4.
  2. Recompute assignments for N=5 (simulating one node joining) and count what percentage of keys changed owners.

Part 2 — Build the consistent hash ring:

  1. Implement the HashRing class from Section 3 with 100 virtual nodes per physical node.
  2. Assign the same 100,000 keys with 4 physical nodes on the ring, then add a 5th node and recompute. Count the percentage of keys that moved.
  3. Confirm the moved percentage is close to the theoretical ideal (roughly 1/N_new, i.e. about 20% for 4→5), nowhere near the near-100% from Part 1.

Part 3 — Measure load balance:

  1. With 4 physical nodes, compare how evenly keys are distributed using 1 virtual node per physical node vs. 100. Report the min/max key count per node for each.
Hint

With only 1 virtual node per physical node, expect a noticeably lopsided distribution — some nodes get much larger arcs than others purely by the luck of where their single hash landed. More virtual nodes average that luck out.

7. Knowledge Check

5 quick questions. Expand each to check your answer.

Q1

Why does range partitioning on a timestamp or auto-increment key tend to create a hot spot?

Because every new write has a key larger than all previous ones, it always falls into the "latest" range partition, so that one partition absorbs all write traffic while every other partition sits idle.

Q2

What does hash partitioning cost you compared to range partitioning?

Sorted order across keys. Because hashing scatters consecutive keys across partitions, an efficient range scan (e.g. "all orders from March") is no longer possible against one partition — it has to query every partition and merge the results.

Q3

Why does adding one node under plain hash(key) % N remap almost every key, while consistent hashing remaps only a fraction?

Changing N changes the modulus used for every key's calculation, so most keys land on a different result even though only one node changed. Consistent hashing fixes positions on a ring; adding a node only takes over the single arc between it and its clockwise neighbor, leaving every other key's owner unchanged.

Q4

What problem do virtual nodes solve that plain consistent hashing (one position per physical node) doesn't?

With only one ring position per node, arc sizes (and therefore load) can be very uneven by chance, and a single node joining or leaving moves one large, concentrated chunk of keys. Many small virtual-node arcs per physical node average out the load and spread any rebalance across more of the cluster.

Q5

A document-partitioned (local) secondary index makes writes cheap but reads expensive. Why?

Each partition only indexes its own local data, so a write only ever touches its own partition's index — cheap. But a query on the secondary field doesn't know which partition holds matching rows, so it must fan out to every partition and merge the results (scatter-gather) — expensive.
