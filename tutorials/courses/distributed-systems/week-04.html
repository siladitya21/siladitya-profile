Week 4: RPC, Retries & Delivery Semantics

Weeks 1–3 established that a request can time out without telling you whether it ran. This week turns that into engineering practice: how to set timeouts and deadlines, how to retry without overwhelming a struggling service, what at-most-once, at-least-once and "exactly-once" really mean, and the idempotency-key pattern that makes retries safe for operations like payments.

Module 1 of 5 Week 4 of 16 ~3 Hours Hands-on Exercise Included

By the end of this week, you'll be able to

  • Explain why remote procedure calls can't be treated like local function calls
  • Implement retries with exponential backoff, jitter, deadlines and a retry budget
  • Make a non-idempotent operation safe to retry using an idempotency key

1. A Remote Call Is Not a Local Call

Remote procedure call (RPC) frameworks such as gRPC, Thrift, or plain HTTP+JSON clients make a network request look like an ordinary function call: user = users.get(42). That's convenient, and also misleading. A 1994 Sun Microsystems paper, "A Note on Distributed Computing" (Waldo et al.), argued that hiding the network this way is fundamentally flawed, because remote calls differ from local ones in ways no framework can paper over:

local call vs. remote call
                     LOCAL CALL                 REMOTE CALL
outcome              returns or throws          returns, throws, OR TIMES OUT
                                                (outcome unknown — Week 1)
latency              nanoseconds, predictable   ms to seconds, highly variable
partial failure      no                         the callee may be down
                                                while you're fine
arguments            passed by reference        serialized; no shared memory
retries              never needed               needed — but may duplicate
                                                the side effect
versioning           compiled together          caller & callee deploy
                                                independently

The rest of this lesson is about the third row of outcomes: what a caller should do once it accepts that "timed out" is a normal result, not an exotic error.

2. Timeouts & Deadline Propagation

Every remote call needs a timeout. Without one, a single hung dependency holds a thread, connection or socket forever, and enough of those take the caller down too. A good starting point is to base timeouts on measured latency, such as a little above the dependency's p99, rather than on round numbers.

In a chain of services, per-hop timeouts aren't enough. If the user-facing request has a 2-second budget, a service three hops deep shouldn't start a 2-second call when only 200 ms of the budget remain. A deadline is an absolute point in time that travels with the request, and each hop works with whatever is left:

deadline propagation — python-style pseudocode
import time

def handle_checkout(req):
    deadline = time.monotonic() + 2.0            # total budget for this request
    cart  = call(cart_service,  req, deadline)
    price = call(pricing,       cart, deadline)
    return call(payments,       price, deadline)

def call(service, payload, deadline):
    remaining = deadline - time.monotonic()
    if remaining <= 0.01:
        raise DeadlineExceeded()                 # don't start work that can't finish
    # gRPC does this natively: the deadline is sent in request metadata
    return service.invoke(payload, timeout=remaining)
Deadlines save the callee too

When a deadline arrives with the request, a backend can skip work whose caller has already given up, instead of computing an answer nobody will read. Under overload, this is often the difference between recovering and collapsing.

3. Retrying Without Making Things Worse

Retrying is the obvious response to a timeout, and naïve retries are a classic way to turn a small blip into an outage. If a service slows down because it's overloaded, and every client immediately retries, its load multiplies at the worst possible moment: a retry storm. Four rules keep retries safe:

  • Retry only what's retryable: timeouts, connection errors, 503s and 429s. Don't retry a 400 Bad Request; it will fail the same way every time.
  • Back off exponentially: wait longer after each failure, giving the service room to recover.
  • Add jitter: randomize the waits so that thousands of clients that failed together don't all retry in lockstep.
  • Cap the effort: limit the number of attempts, respect the deadline, and use a retry budget (for example, retries may add at most 10% extra load).
exponential backoff with "full jitter" — python
import random, time

RETRYABLE = (TimeoutError, ConnectionError)

def call_with_retries(fn, deadline, base=0.1, cap=5.0, max_attempts=5):
    for attempt in range(max_attempts):
        try:
            return fn()
        except RETRYABLE:
            if attempt == max_attempts - 1:
                raise
            # full jitter: sleep a random amount up to the exponential ceiling
            sleep = random.uniform(0, min(cap, base * 2 ** attempt))
            if time.monotonic() + sleep >= deadline:
                raise                       # no time left to try again
            time.sleep(sleep)
Retries multiply across layers

If a request passes through three services and each layer retries 3 times, one user action can become 3 × 3 × 3 = 27 calls to the bottom service. Retry at one layer (usually the outermost one that knows the request is safe to repeat) and let inner layers fail fast.

4. At-Most-Once, At-Least-Once, "Exactly-Once"

Your retry policy decides your delivery semantics: how many times an operation may take effect when failures happen.

the three semantics
AT-MOST-ONCE    send once, never retry.
                effect happens 0 or 1 times — may be LOST.
                fine for: metrics samples, best-effort notifications.

AT-LEAST-ONCE   retry until acknowledged.
                effect happens 1 or more times — may be DUPLICATED.
                the default for queues (SQS, Kafka consumers) and most RPC
                retry logic.

EXACTLY-ONCE    effect happens exactly 1 time.
                as a DELIVERY guarantee over an unreliable network it's
                impossible in general (Two Generals, Week 2).
                as a PROCESSING guarantee it IS achievable:
                    at-least-once delivery  +  idempotent/deduplicated processing
                    = "effectively-once" effect

When a product advertises "exactly-once," read it as "duplicates are deduplicated before they take effect, within a defined boundary." Kafka's exactly-once semantics, for example, apply to reads and writes within Kafka. Once your consumer sends an email or calls a payment API, you need your own idempotency again.

5. Idempotency & Idempotency Keys

An operation is idempotent if doing it twice has the same effect as doing it once. Some operations are naturally idempotent and others aren't:

naturally idempotent vs. not
IDEMPOTENT (safe to retry as-is)       NOT IDEMPOTENT (retry = duplicate)
  SET balance = 500                      balance = balance + 100
  DELETE order 17                        INSERT a new order
  PUT /users/42 {full record}            POST /payments  (charge ₹500)
  add "x" to a set                       append "x" to a list

To make a non-idempotent operation safe, the client generates a unique idempotency key (for example a UUID) once per logical operation and sends the same key with every retry. The server records the key and the result, and if it sees the key again, it returns the stored result instead of doing the work twice. Payment APIs such as Stripe expose exactly this through an Idempotency-Key HTTP header.

server-side idempotency key handling — python + SQL
def create_payment(db, idem_key: str, account: str, amount: int):
    with db.transaction():
        row = db.query_one(
            "SELECT response FROM idempotency WHERE key = %s FOR UPDATE",
            idem_key)
        if row:
            return row.response                  # duplicate: replay old answer

        result = charge(db, account, amount)     # the real side effect

        # Record the key IN THE SAME TRANSACTION as the side effect, so the
        # effect and the record of it can never get out of sync.
        db.execute(
            "INSERT INTO idempotency (key, response) VALUES (%s, %s)",
            idem_key, result)
        return result

# Client: generate the key ONCE, reuse it for every retry of this payment
key = str(uuid.uuid4())
call_with_retries(lambda: api.create_payment(key, "acct_9", 500), deadline)
Generate the key per operation, not per attempt

If the client creates a fresh UUID inside the retry loop, every retry looks like a new payment and you're back to double charges. The key identifies the user's intent ("pay for order 1234"), so it must be created before the first attempt.

A unique constraint is the backstop

Two concurrent retries could both miss the SELECT and race. A PRIMARY KEY or UNIQUE constraint on the idempotency key column makes the second INSERT fail, rolling back its transaction and its duplicate charge with it. Let the database enforce uniqueness rather than trusting application logic alone.

7. Knowledge Check

5 quick questions. Expand each to check your answer.

Q1

List two ways a remote call differs from a local function call that no RPC framework can hide.

Any two of the following: a remote call can time out with an unknown outcome; its latency is far higher and more variable; the callee can fail independently of the caller (partial failure); arguments must be serialized because there's no shared memory; retries can duplicate side effects; caller and callee can run different versions.

Q2

Why add jitter to exponential backoff, rather than having every client wait exactly 100 ms, 200 ms, 400 ms and so on?

Clients that failed at the same moment (because the service hiccupped) would otherwise retry at exactly the same moments, hitting the recovering service in synchronized waves. Random jitter spreads those retries out over time, smoothing the load.

Q3

Is exactly-once delivery possible over an unreliable network? What do systems that advertise "exactly-once" actually provide?

Exactly-once delivery isn't possible in general, because a sender can never be sure its last message arrived (Two Generals). What's achievable is an exactly-once effect: deliver at least once, and deduplicate or make processing idempotent so duplicates don't take effect twice. This holds only within the boundary where deduplication is enforced.

Q4

Which of these operations is naturally idempotent: (a) "set the user's email to x", (b) "add ₹100 to the balance", (c) "delete order 17"?

(a) and (c) are idempotent: doing them twice leaves the same state as doing them once. (b) is not, because each repetition adds another ₹100, so it needs an idempotency key or a rewrite as an absolute or conditional update.

Q5

Why must the server record the idempotency key in the same transaction as the side effect?

If they are separate steps, a crash between them leaves the system inconsistent. Either the effect happened without the key being recorded (so a retry duplicates it), or the key was recorded without the effect (so a retry wrongly returns success for work that never happened). One atomic transaction makes both happen together or not at all.
