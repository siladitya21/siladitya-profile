Week 15: Testing & Operating Distributed Systems

Every failure mode from this course — partial failure, clock skew, lost and reordered messages, split brain, conflicting writes — only turns into a real bug under a specific, often rare timing of events. This week is about finding those bugs on purpose: injecting the faults instead of hoping they don't happen, making them perfectly reproducible, and keeping a running system honest about how it's actually behaving once it's live.

Module 5 of 5 Week 15 of 16 ~3 Hours Hands-on Exercise Included

By the end of this week, you'll be able to

  • Explain why distributed bugs rarely show up in ordinary unit tests
  • Describe Jepsen-style fault injection and what a linearizability checker verifies against it
  • Explain deterministic simulation testing and what TLA+ model-checking is for
  • Use distributed tracing and SLOs to reason about a live system's real behavior

1. Why Distributed Bugs Hide

This entire course has been a catalog of failure modes: partial failure and lost messages (Weeks 1–2), clock skew (Week 3), replication lag and split brain (Week 5), lost updates (Week 6), stale quorum reads (Weeks 8–9), stale leaders (Weeks 5 and 10). Every one of those bugs only manifests under a specific interleaving of timing: a message arriving a few milliseconds later than usual, a node pausing at exactly the wrong instant, a partition healing in the middle of an election.

Ordinary unit tests run on one machine, with no real network and almost no timing variation, so they systematically miss exactly this class of bug. "Works on my machine, and in CI" is barely evidence at all for a system whose scariest bugs require conditions a single-machine test can't even represent, let alone reproduce on demand.

2. Jepsen-Style Testing & Fault Injection

Jepsen is a testing approach (and a widely-used tool) that runs a real system under a generated sequence of client operations while actively injecting real faults — partitioning the network with firewall rules, skewing clocks, killing processes — and then checks the resulting history of operations against a target consistency model, using a model-checker like Knossos to verify whether the observed history could have come from, say, a linearizable system (Week 8's exact definition, now checked mechanically instead of by hand).

the Jepsen loop
1. generate a history of concurrent client operations (reads, writes)
2. run them against the REAL system, under REAL injected faults
   (network partitions, clock jumps, process kills — Weeks 1-5's
    failure modes, induced on purpose instead of hoped against)
3. record what actually happened: every operation's start, end, result
4. feed the recorded history to a CHECKER
   → does this history satisfy linearizability (or whatever model
     the system claims)? if not: PRODUCE A COUNTEREXAMPLE

Jepsen-style fault injection is a specific case of the more general idea of chaos engineering at the testing stage: deliberately breaking things in a controlled environment to find the system's actual failure modes, rather than waiting to discover them from an incident.

3. Deterministic Simulation & a First Look at TLA+

Deterministic simulation testing (DST) takes a different angle: run the entire distributed system inside a single process, with a simulated clock and a simulated network standing in for real time and real sockets, all driven by one pseudo-random seed. Because every timer firing, every message delay, and every scheduling decision flows from that one seed, the exact same seed reproduces the exact same run byte-for-byte — a property real distributed tests almost never have. This makes it practical to run millions of simulated hours across thousands of random seeds in minutes, hunting for the one seed that reveals a bug, and then replay that exact seed to debug it deterministically (this is the approach FoundationDB popularized, and it's the same idea Week 10's exercise hint already pointed at with a seeded simulation harness).

TLA+ attacks the same problem from a completely different angle: before any code exists, describe a protocol's possible states and the transitions between them as a formal specification, then exhaustively model-check every reachable state (for a small enough state space) against a stated safety property — exactly the kind of property Week 10's election-restriction proof argued about informally, now checked mechanically for every possible interleaving instead of the handful a person can reason through. Teams at AWS, MongoDB and others have used TLA+ specifically on consensus-adjacent protocols like the ones in Weeks 9–10, finding subtle bugs in designs before a single line of implementation was written.

DST and Jepsen answer different questions

DST tells you whether your design, exhaustively explored in a fast, fully reproducible fake environment, is correct. Jepsen tells you whether your actual running implementation, under real (if constrained) faults, behaves the way it claims to. Mature systems tend to use both, not one instead of the other.

4. Distributed Tracing, SLOs & Chaos Engineering in Production

Testing finds bugs before release; three more tools keep a live system honest after it ships. Distributed tracing propagates one trace id across every hop of a request (Week 4's RPC chain, now instrumented), so when something is slow or wrong, you can reconstruct the exact path a request took across a dozen services and see precisely which hop the time or the error actually came from — essential once "slow" could mean any of a dozen different causes spread across a dozen different machines.

An SLO (service level objective) states a measurable target — "99.9% of requests under 200ms" — and the gap between that target and perfect reliability is an error budget: a concrete, numeric amount of acceptable failure that can be spent on shipping faster, or hoarded by freezing risky changes when the budget is nearly used up. It turns "is this safe to ship" from a gut feeling into a number.

Chaos engineering takes Section 2's fault injection out of the test environment and into production itself, under a deliberately controlled blast radius: inject a real fault into a small, bounded slice of live traffic, on the theory that a system should be routinely exercised against exactly the failures it claims to tolerate, rather than discovering the gap between "claims to tolerate" and "actually tolerates" during a real incident.

5. Hands-on Exercise

Hands-on

Build a deterministic simulation harness around Week 10's Raft election, and fuzz it

Part 1 — Seed the simulation:

  1. Take the Raft leader-election simulation from Week 10's exercise and route every random decision (election timeout values, simulated message delays, delivery order) through a single seeded pseudo-random generator.
  2. Run the same seed twice and confirm the two runs produce byte-for-byte identical outcomes — the defining property of deterministic simulation.

Part 2 — Fuzz for a safety violation:

  1. Write a checker for one safety property from Week 10: "at most one leader exists per term."
  2. Run the simulation across 1,000 different seeds, and have the checker flag any run that violates the property.
  3. If you find a violating seed, note it down — that seed now deterministically reproduces the bug on demand, every time, which is the entire point.

Part 3 — A tiny Jepsen-style check:

  1. Reuse the linearizability checker you built in Week 9's or Week 10's exercises (or write a small one now) against a log of (client, op, start_time, end_time, value) entries from one of your earlier toy systems.
  2. Deliberately introduce a fault (route one read to a stale replica) and confirm the checker flags a violation; remove the fault and confirm it doesn't.
Hint

If you can't reproduce a bug a second time from the same seed, something outside the seed — real wall-clock time, a dict's iteration order, an unseeded library call — is leaking randomness into the run. Finding and removing that leak is itself most of the real engineering work behind deterministic simulation.

6. Knowledge Check

5 quick questions. Expand each to check your answer.

Q1

Why do ordinary single-machine unit tests tend to miss the most dangerous distributed-systems bugs?

Those bugs only manifest under specific timing interleavings — a message delayed by a few milliseconds, a pause at exactly the wrong moment — and a single-machine test with no real network has almost no timing variation to trigger them.

Q2

What does a Jepsen-style test check the recorded operation history against?

A target consistency model, such as linearizability, using a model-checker to determine whether the recorded history of operations could actually have come from a system that satisfies that model.

Q3

What property of deterministic simulation testing makes a discovered bug reliably debuggable, rather than a one-time flake?

Every source of randomness (timers, delays, scheduling) flows from one pseudo-random seed, so re-running the same seed reproduces the exact same run byte-for-byte — a bug found under one seed can always be replayed on demand.

Q4

What question does TLA+ model-checking answer that deterministic simulation and Jepsen don't directly answer?

Whether a protocol's DESIGN itself is correct, by exhaustively exploring every reachable state of a formal specification against a safety property — checked before any implementation exists, rather than testing a particular running system (Jepsen) or a particular simulated implementation (DST).

Q5

What does an error budget turn a "is this safe to ship" decision into?

A concrete number — the measurable gap between an SLO's target and perfect reliability — that can be explicitly spent on shipping riskier changes faster, or preserved by freezing risky changes once it's nearly exhausted, instead of a subjective gut-feeling judgment call.
