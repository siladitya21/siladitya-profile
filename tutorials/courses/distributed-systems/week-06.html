Week 6: Multi-Leader & Leaderless Replication

A single leader is a single place writes can happen — fine until you need writes to succeed in two data centers at once, or to keep working while any one node is down. This week looks at two topologies that accept writes in more than one place: multi-leader replication, where each leader's writes must eventually be reconciled with the others', and Dynamo-style leaderless replication, where quorums of reads and writes stand in for a leader entirely, backed by read repair and anti-entropy to keep replicas converging.

Module 2 of 5 Week 6 of 16 ~3 Hours Hands-on Exercise Included

By the end of this week, you'll be able to

  • Explain why a system would accept writes in more than one place, and what it costs
  • Describe multi-leader topologies and at least two conflict-resolution strategies
  • Reason about Dynamo-style N/R/W quorums and when reads are guaranteed to see the latest write
  • Explain how read repair, anti-entropy and Merkle trees keep leaderless replicas converging

1. Why Accept Writes in More Than One Place

Leader-follower replication has one structural weakness: while the leader is unreachable from some part of the network, that part cannot write at all. Three situations push systems past that limit:

  • Multiple data centers: a single leader means every write in Tokyo crosses the ocean to a leader in Virginia. Letting Tokyo have its own leader removes that latency.
  • Offline-first clients: a mobile app or a laptop that keeps working (and writing) with no network at all is, in effect, its own leader until it reconnects and syncs.
  • Availability during partitions: if any reachable replica can accept a write, a network split no longer stops writes on either side of it.

All three buy availability by giving up something leader-follower replication gave you for free: a single, globally agreed order of writes. Once two nodes can each accept a write to the same key before either has heard about the other's, the system must decide what to do when those writes conflict. This week covers two topologies that make that trade and the machinery each needs to recover from it.

2. Multi-Leader Topologies & Conflict Resolution

In multi-leader replication, each data center (or client) has its own leader, which replicates to its local followers and also exchanges writes with the other leaders:

multi-leader topology — two data centers
  DATA CENTER A                      DATA CENTER B
  writes --> LEADER A <----cross-replication----> LEADER B <-- writes
                 |                                     |
            followers A                           followers B

If a key is updated in both data centers before either update reaches the other, both leaders eventually see two different values for the same key with no inherent order between them — a write conflict. Three common ways to resolve one:

  • Last-write-wins (LWW): attach a timestamp (or a Lamport clock from Week 3) to every write; on conflict, keep the one with the higher timestamp. Simple, but it silently discards one write — fine for a cache, risky for anything a user cares about.
  • Application-specific merge: let the domain define the merge, e.g. a shopping cart conflict merges to the union of both carts' items rather than picking one side.
  • Convergent replicated data types: design the value itself so concurrent updates always merge the same way, no matter what order they're applied in. Week 13 covers CRDTs in depth.
last-write-wins with a tiebreak — python-style pseudocode
def resolve_conflict(write_a, write_b):
    # each write carries (lamport_timestamp, node_id, value) — Week 3
    if write_a.ts != write_b.ts:
        return write_a if write_a.ts > write_b.ts else write_b
    # ties (rare, but possible with Lamport clocks) break on node_id
    # so every replica picks the SAME winner deterministically
    return write_a if write_a.node_id > write_b.node_id else write_b
Wall-clock LWW can lose a "later" write

If timestamps come from unsynchronized wall clocks (Week 3), a write from a node with a fast clock can beat a genuinely later write from a node with a slow one. A logical clock, or an explicit version vector that detects concurrency instead of guessing at ordering, avoids this.

3. Leaderless Replication & Dynamo-Style Quorums

Leaderless replication (the Dynamo/Cassandra/Riak model) removes the leader entirely. For a dataset replicated across N nodes, a client writes directly to multiple replicas and reads from multiple replicas, using two tunable numbers:

  • W — the write succeeds once W of the N replicas have acknowledged it.
  • R — a read queries R of the N replicas and returns the newest value among their responses.
the quorum overlap rule
If  W + R > N
then every read quorum and every write quorum share at least one node —
so a read is guaranteed to see the most recent SUCCESSFUL write.

example: N=3, W=2, R=2  →  W+R=4 > 3   ✓ overlap guaranteed
example: N=3, W=1, R=1  →  W+R=2 <= 3  ✗ a read can miss the latest write
leaderless client write/read — python-style pseudocode
def write(key, value, replicas, N, W):
    version = new_version_vector(key, replicas)
    acked = 0
    for r in replicas:
        if r.put(key, value, version):
            acked += 1
    if acked < W:
        raise WriteFailed()           # could not reach a write quorum

def read(key, replicas, N, R):
    responses = [replicas[i].get(key) for i in sample(replicas, R)]
    return newest_by_version(responses)   # may trigger read repair — Section 4

Smaller W and R buy lower latency and more availability (fewer nodes must be reachable); larger values buy stronger consistency. W=N, R=1 behaves like synchronous replication for writes; W=1, R=N pushes the cost onto reads instead.

4. Read Repair & Anti-Entropy with Merkle Trees

Quorums alone don't make replicas identical — a slow or temporarily unreachable node still holds a stale value after a write, even one that met its write quorum. Two background mechanisms close that gap:

Read repair happens inline: when a read queries R replicas and sees that one returned an older version than the others, the client (or coordinator) writes the newer value back to the stale replica right then. It's opportunistic — it only fixes keys that actually get read.

Anti-entropy runs in the background, independent of reads, comparing replicas wholesale and repairing whatever read repair never touched. Comparing every key between two large replicas byte-by-byte is expensive, so systems compare Merkle trees instead — a tree of hashes where each parent hash is a hash of its children. Two replicas with identical data have identical root hashes in O(1) comparisons; where the roots differ, only the diverging branches need to be walked and compared.

merkle tree comparison — python-style pseudocode
def diff(node_a, node_b):
    if node_a.hash == node_b.hash:
        return []                              # subtrees identical — stop here
    if node_a.is_leaf():
        return [node_a.key]                    # found a divergent key
    mismatches = []
    for child_a, child_b in zip(node_a.children, node_b.children):
        mismatches += diff(child_a, child_b)   # recurse only where hashes differ
    return mismatches
Why this matters

Without Merkle trees, finding the handful of keys that differ between two replicas holding millions of rows means transferring and comparing all of them. With a Merkle tree, the cost is proportional to how much actually diverged, not to how much data exists.

5. Sloppy Quorums & Hinted Handoff

The quorum rule in Section 3 assumes a write always lands on the N nodes officially responsible for a key. If enough of those specific nodes are down, a strict quorum blocks writes entirely — exactly the availability leaderless replication was meant to buy back. A sloppy quorum relaxes this: if fewer than W of the "home" nodes are reachable, the write is accepted on any W reachable nodes instead, even ones not normally responsible for that key.

Those substitute nodes hold the write temporarily. Once a home node comes back, the data is forwarded to it and removed from the stand-in — hinted handoff.

Sloppy quorums break the W+R>N guarantee

A write accepted on stand-in nodes means the home nodes a read actually queries may not have it yet. Sloppy quorums trade the "a quorum read always sees the latest quorum write" guarantee from Section 3 for more availability. Dynamo and Cassandra both make this an explicit, tunable choice rather than a hidden one.

6. Hands-on Exercise

Hands-on

Build a toy Dynamo-style key-value store with N=3, W=2, R=2

Three in-process "nodes" (plain dicts behind a small interface) stand in for replicas.

Part 1 — Quorum writes and reads:

  1. Implement write(key, value) that writes to all 3 nodes but only waits for 2 acks, and read(key) that queries 2 nodes and returns the response with the higher version.
  2. Kill one node (stop routing to it) and confirm writes and reads still succeed.

Part 2 — Detect a real conflict:

  1. Attach a version vector (Week 3) to every value instead of a single counter.
  2. Simulate two "concurrent" writes to the same key on two different nodes before either replicates, then read: your code should detect that the version vectors are concurrent (neither dominates the other), not just pick one by timestamp.
  3. Resolve the conflict with a simple application-specific merge (e.g. if the value is a set, union both sides) rather than LWW, and confirm no update is silently dropped.

Part 3 — Read repair:

  1. After resolving a conflict in Part 2, have the read path write the merged value back to whichever node(s) returned the older version.
  2. Read the key again and confirm all 3 nodes now agree, without running any separate anti-entropy step.
Hint

If you use plain timestamps instead of version vectors in Part 2, you can't tell a real conflict apart from a write that simply happened later — that's exactly the LWW trap from Section 2's warning callout.

7. Knowledge Check

5 quick questions. Expand each to check your answer.

Q1

Name two situations that push a system toward accepting writes in more than one place.

Any two of: multiple data centers wanting a local leader to avoid cross-region latency, offline-first clients that must keep writing with no network, and wanting writes to keep working on either side of a network partition.

Q2

Why can wall-clock-based last-write-wins discard the "actually later" write?

Because wall clocks on different nodes are never perfectly in sync (Week 3). A write stamped by a node whose clock runs fast can show a higher timestamp than a genuinely later write stamped by a node with a slower clock, so LWW keeps the wrong one.

Q3

For N=5 replicas, give values of W and R that guarantee a read sees the latest successful write, and one pair that doesn't.

Any W and R with W+R>5 guarantees overlap, e.g. W=3, R=3 (sum 6). W=2, R=2 (sum 4 <= 5) does not guarantee it — a read quorum and a write quorum of those sizes can fail to share a node.

Q4

What is the difference between read repair and anti-entropy?

Read repair fixes a stale replica opportunistically, only when a read happens to touch that key. Anti-entropy is a background process that compares replicas wholesale (efficiently, using Merkle trees) and repairs divergence whether or not anyone ever reads those keys.

Q5

What does a sloppy quorum trade away, and what mechanism moves data back to its home nodes afterward?

It trades away the guarantee that a quorum read overlaps with every quorum write, since the write may have landed on stand-in nodes instead of the key's home nodes. Hinted handoff moves the data to the correct home nodes once they're reachable again.
