Week 5: Leader-Follower Replication

One machine holding your data is a single point of failure, a read bottleneck and a latency problem for anyone far from it. Replication fixes all three by keeping copies of the data on multiple machines. This week covers the simplest and most common topology — one leader, many followers — how synchronous and asynchronous replication trade durability for latency, why followers lag behind and what that breaks for readers, and how to fail over to a new leader without losing acknowledged writes.

Module 2 of 5 Week 5 of 16 ~3 Hours Hands-on Exercise Included

By the end of this week, you'll be able to

  • Explain the three reasons systems replicate data, and how a leader-based topology orders writes
  • Compare synchronous, asynchronous and semi-synchronous replication on durability vs. latency
  • Diagnose replication lag and implement read-your-writes and monotonic-read guarantees
  • Promote a new leader after a failure without creating a split brain

1. Why Replicate Data at All

There are three independent reasons to keep more than one copy of your data, and a real system usually wants all three at once:

  • Durability: if the only copy of a row lives on one disk, that disk's failure deletes the row. A second copy on a second machine survives it.
  • Read scalability: a single machine can only serve so many reads per second. Spreading reads across copies multiplies read capacity.
  • Latency: a user in Mumbai reading from a server in Virginia pays a half-second round trip. A nearby copy removes it.

The topology this week is leader-follower (also called primary-replica or master-slave) replication: one node, the leader, accepts all writes. Every write is appended to the leader's write-ahead log in a fixed order, and that same ordered log is streamed to every follower, which replays it to stay in sync. Because every follower applies the exact same sequence of writes, replication turns into "agree on an order, then everyone replays it" — the same idea you'll see generalized into a replicated state machine when Raft appears in Week 10.

leader-follower topology
            writes
 client -------------> LEADER  (keeps the ordered write-ahead log)
                          |  streams log
                 ---------+---------
                 |                 |
             FOLLOWER A        FOLLOWER B
            (replays log)     (replays log)
                 ^                 ^
                 |  reads          |  reads
              client            client

2. Synchronous vs. Asynchronous Replication

Once the leader has appended a write to its own log, it must decide how long to wait before telling the client "done." That choice is the whole trade-off:

three replication modes
SYNCHRONOUS      leader waits for ALL followers to ack before replying.
                 durability: strongest — a confirmed write exists on every replica.
                 latency:    bounded by the SLOWEST follower; one stuck follower
                             stalls every write.

ASYNCHRONOUS     leader replies as soon as it has written locally; followers
                 catch up whenever they can.
                 durability: weakest — if the leader dies before shipping a
                             write, that write is gone, even though the client
                             was told "done."
                 latency:    lowest; unaffected by follower health.

SEMI-SYNCHRONOUS leader waits for acks from a QUORUM (e.g. 1 of 2 followers,
                 or any majority) before replying; the rest catch up async.
                 durability: a confirmed write survives the leader failing,
                             as long as a quorum follower is promoted.
                 latency:    bounded by the fastest quorum, not the slowest
                             follower.
leader write path, parameterized by mode — python-style pseudocode
def leader_write(record, mode, followers):
    local_offset = wal.append(record)          # 1. always write locally first

    if mode == "async":
        for f in followers:
            f.ship_async(record)                # fire-and-forget
        return "ok"                             # 2a. reply immediately

    acks_needed = len(followers) if mode == "sync" else quorum_size(followers)
    acked = 0
    for f in followers:
        f.ship(record)
    while acked < acks_needed:
        acked += wait_for_next_ack()            # 2b. block until enough acks
    return "ok"

Most production databases default to asynchronous replication for low latency, and offer semi-synchronous as an opt-in for data that must never be lost on failover — MySQL's semi-sync plugin and PostgreSQL's synchronous_standby_names both implement exactly the quorum-ack pattern above.

"Durable" is a claim about failover, not about the leader alone

Synchronous replication only protects you if the system actually promotes a follower that has the write when the leader dies. Section 4 covers the promotion logic that makes that true in practice.

3. Replication Lag & What It Breaks for Readers

With asynchronous (or semi-synchronous) replication, a follower is always some distance behind the leader — its replication lag. Under normal load that's milliseconds; under load spikes or network trouble it can grow to seconds or minutes. Lag is invisible until an application reads from a follower and gets a surprising answer. Two concrete guarantees describe the surprises and how to prevent them.

Read-your-writes: a user submits a comment, the page redirects to the comment thread, and a read hits a follower that hasn't received the write yet — the user's own comment appears to vanish. Fixes:

  • Route reads for data the user just wrote to the leader for some time window after the write.
  • Track a version/offset with the write; the client remembers it and a follower rejects (or stalls) the read until its applied offset reaches that version.

Monotonic reads: a user refreshes a page twice in quick succession, each request lands on a different follower, and the second (more lagged) follower shows older data than the first — time appears to run backward. Fix: route every read in a session to the same follower (sticky routing), so a user's own view never regresses even if it's a little stale.

version-aware read-your-writes — python-style pseudocode
def write(leader, record):
    offset = leader.append(record)
    return offset                       # client remembers this offset

def read(follower, key, min_offset=None):
    if min_offset is not None and follower.applied_offset < min_offset:
        # not caught up yet: wait briefly, or just read from the leader
        follower = leader                # fall back for freshness
    return follower.get(key)
A related guarantee: consistent prefix reads

When writes are causally related (a question, then its answer), a reader must never see the answer without the question. This matters most once data is partitioned across many leaders — Week 13's CRDTs and Week 8's causal consistency both return to this exact problem.

4. Failover & Split Brain

When the leader stops responding (detected with the heartbeats and timeouts from Week 2), something must promote a follower to leader so writes can continue. Two things can go wrong, and both are more dangerous than "the system is down":

  • Lost writes: if the most "available" follower is promoted without checking it has the latest log, writes the old leader acknowledged (and maybe even sent to the client as "done") can disappear.
  • Split brain: the old leader was only partitioned, not dead. It comes back thinking it's still the leader, while a new leader has already been promoted. Now two leaders accept writes independently, and their logs diverge.
safer promotion — python-style pseudocode
def promote_new_leader(candidates, current_epoch):
    # 1. pick the candidate with the FURTHEST-ALONG log, not just "reachable"
    winner = max(candidates, key=lambda f: f.applied_offset)

    # 2. bump an epoch (generation) number — every write and every message
    #    from now on carries this epoch
    new_epoch = current_epoch + 1
    winner.become_leader(new_epoch)
    return winner, new_epoch

def on_message_from_leader(msg):
    # 3. any node rejects messages tagged with an OLDER epoch than it has
    #    already seen — this is what stops a reawakened old leader cold
    if msg.epoch < self.current_epoch:
        return reject("stale leader")
    self.current_epoch = msg.epoch
    apply(msg)

The epoch (Raft calls it a term) is the cheap half of the fix: every node simply refuses instructions from a leader whose epoch it has already superseded. The harder half is agreeing on who the new leader is in the first place — which needs a majority vote, not a single node's opinion. That's exactly the consensus problem Weeks 9–10 solve properly with Paxos and Raft; for now, treat "a human runs a failover script" or "a quorum-based tool like Patroni decides" as the stand-in.

Fencing the old leader isn't optional

Rejecting stale epochs in software is necessary but, for truly critical systems, not sufficient — a leader stuck in a kernel-level hang might still be able to write to shared storage. Hardware-level fencing ("shoot the other node in the head," STONITH) is the belt-and-suspenders version. Week 11 picks this up again with fencing tokens from a coordination service.

5. Hands-on Exercise

Hands-on

Build a toy leader-follower log and break (then fix) read-your-writes

Simulate the whole chapter in-process with threads or asyncio tasks standing in for machines.

Part 1 — Async replication with visible lag:

  1. Build a Leader with an in-memory list as its write-ahead log, and two Follower objects that each run a background task replaying the leader's log into their own list, with a random 50–300ms delay per entry to simulate lag.
  2. Write a value, then immediately read it from a follower. Confirm the value is sometimes missing — you've reproduced the read-your-writes bug.

Part 2 — Fix it with a version check:

  1. Have every write return the leader's log offset after appending.
  2. Change reads to take a min_offset; if the chosen follower's applied offset is behind it, read from the leader instead.
  3. Re-run the test from Part 1 in a loop 200 times and confirm the bug no longer reproduces.

Part 3 — Simulate failover:

  1. Stop the leader mid-stream, after it has acked a write to only one of the two followers (simulating async replication).
  2. Promote whichever follower has the higher applied offset; assign it a new epoch number one higher than the last seen.
  3. Bring the old leader back and have it try to ship one more write tagged with the old epoch; confirm both followers reject it.
Hint

If you promote the follower with the lower offset in Part 3 instead, you'll silently lose the write the other follower had. Run it both ways and compare the final log contents — that's the lost-write bug made visible.

6. Knowledge Check

5 quick questions. Expand each to check your answer.

Q1

Name the three independent reasons a system replicates data.

Durability (a copy survives a machine/disk failure), read scalability (reads spread across copies), and latency (a nearby copy avoids a long round trip).

Q2

Why does semi-synchronous replication usually have lower latency than fully synchronous, while still protecting confirmed writes on failover?

It only waits for a quorum (e.g. one of two followers) rather than every follower, so it's bounded by the fastest acknowledging follower, not the slowest. A write is still safe because the failover logic only needs to promote a follower from that same quorum, which is guaranteed to have the write.

Q3

A user posts a comment and the page immediately reloads, reading from a follower — and the comment is missing. Which guarantee is violated, and name one fix.

Read-your-writes. Fix: route the read to the leader shortly after the write, or have the client remember the write's offset and have the follower wait until it reaches that offset (or fall back to the leader) before answering.

Q4

What does an epoch (term) number prevent during failover, and what happens to a message tagged with a stale epoch?

It prevents split brain: a reawakened old leader (or any node) that sends a message with an epoch lower than what a receiver has already seen gets that message rejected, so the stale leader can't keep writing as if nothing happened.

Q5

During failover, why must the promoted follower be the one with the furthest-along log, not simply the first one that responds?

If a less up-to-date follower becomes the new leader, writes that were already acknowledged to clients but only reached the more up-to-date follower are silently lost from the new leader's log — a durability promise broken right when failover was supposed to honor it.
