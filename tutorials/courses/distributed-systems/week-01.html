Week 1: What Makes a System Distributed

A distributed system is any system where independent machines cooperate over a network to do one job — which describes almost every application you have ever used. This week sets up the mental model for the rest of the course: why we accept the enormous extra complexity of spreading work across machines, the single property (partial failure) that makes it so hard, and the false assumptions that quietly break real systems.

Module 1 of 5 Week 1 of 16 ~2.5 Hours Hands-on Exercise Included

By the end of this week, you'll be able to

  • Explain the three main reasons systems are distributed, and the cost each one carries
  • Describe partial failure and why a missing response is fundamentally ambiguous
  • Name the eight fallacies of distributed computing and spot them in a real design

1. Why Distribute at All?

Leslie Lamport's famous joke definition is still the most honest one: "A distributed system is one in which the failure of a computer you didn't even know existed can render your own computer unusable." Nobody distributes a system for fun — a single machine is simpler to build, test, debug and reason about. We pay the complexity cost only when a single machine can't give us one of three things:

  • Scalability — the data or traffic is bigger than one machine can hold or serve, even the biggest one you can buy.
  • Fault tolerance & availability — one machine is one point of failure. If the service must survive a disk dying, a power cut or a whole datacenter going dark, the data has to live in more than one place.
  • Latency — light in fibre covers roughly 200 km per millisecond, so a user in Mumbai talking to a server in Virginia pays well over 100 ms per round trip no matter how fast the server is. Putting copies near users is the only fix.
scale up vs. scale out
SCALE UP (vertical)                    SCALE OUT (horizontal)
  one bigger machine                     many ordinary machines
  + simple: one copy of the data         + no hard ceiling on capacity
  + no network between components        + survives individual failures
  - hard ceiling (biggest box sold)      - every interaction crosses a network
  - still one point of failure           - components fail independently
  - price grows faster than capacity     - you now need everything in this course

Some systems are also distributed by nature rather than by choice: a mobile app and its backend, two banks settling a payment, or sensors reporting to a cloud service are separate machines no matter how small the workload is.

Rule of thumb

Exhaust the single-machine option first. A modern server with dozens of cores, hundreds of GB of RAM and fast NVMe storage handles far more than most people expect — and replicating it for fault tolerance (Module 2) is a much smaller step than redesigning everything around partitioned data.

2. Partial Failure: The Defining Problem

A program on one computer usually fails in a tidy way: it works, or the whole process (or machine) crashes. Either way, you know. In a distributed system, some parts fail while others keep running, and the parts that are still running often can't tell which parts failed. This is called partial failure, and it is the root of nearly every hard problem in this course.

Consider the simplest possible interaction: node A sends a request to node B and waits for a reply that never arrives. From A's point of view, every one of these is possible:

A sent a request and heard nothing back — what happened?
  A ──request──▶ B            ...silence...

  1. The request was lost in the network        (B never saw it)
  2. The request is stuck in a queue somewhere  (B will see it... later)
  3. B crashed before processing it             (nothing happened)
  4. B processed it, then crashed               (it DID happen)
  5. B processed it, but the reply was lost     (it DID happen)
  6. B is just slow — a long GC pause, overload (it WILL happen)

  A cannot tell these cases apart. All it knows is: no reply yet.

Cases 4 and 5 are the dangerous ones: the action happened, but A doesn't know it. If the request was "charge this card ₹500" and A simply retries, the customer may be charged twice. If A gives up, the customer may have been charged with no order recorded. Week 4 is entirely about handling this safely; for now, the key insight is that a timeout tells you that you don't know — not that the operation failed.

Nondeterminism makes bugs hard to reproduce

Partial failures depend on timing: which message was delayed, which node paused, and for how long. A bug that appears once in a million requests in production may never show up on your laptop. Module 5 covers the testing techniques (fault injection, deterministic simulation) built specifically for this.

3. The Eight Fallacies of Distributed Computing

In the 1990s, engineers at Sun Microsystems (L. Peter Deutsch, with the eighth added by James Gosling) wrote down the assumptions that newcomers to distributed systems make — every one of which is false, and every one of which still causes outages today:

the fallacies, and what they break
 #  FALSE ASSUMPTION                 WHAT GOES WRONG WHEN YOU BELIEVE IT
 1  The network is reliable          No retries / no timeouts -> hung requests,
                                     lost writes
 2  Latency is zero                  "Chatty" designs: 200 tiny calls per page load
 3  Bandwidth is infinite            Shipping whole datasets when you needed a row
 4  The network is secure            Plaintext internal traffic, trusted callers
                                     that shouldn't be
 5  Topology doesn't change          Hard-coded IPs; breaks on autoscaling,
                                     failover, redeploys
 6  There is one administrator       Conflicting configs, firewalls & upgrade
                                     schedules you don't control
 7  Transport cost is zero           Serialization CPU and cross-region data
                                     transfer bills
 8  The network is homogeneous       Mixed versions, protocols & hardware that
                                     interpret the same bytes differently

Fallacies 1 and 2 matter most for this course. Every algorithm from Week 5 onward exists precisely because the network is not reliable and latency is not zero — replication, consensus and distributed transactions are all elaborate answers to "what do we do when messages are slow, lost, duplicated or reordered?"

Treat the list as a design-review checklist

When you review an architecture diagram, put your finger on each arrow between boxes and ask the eight questions. "What happens if this arrow is slow? Down? Called twice? Pointing at a box that just moved?" Most production incidents live on those arrows, not inside the boxes.

4. Latency Numbers That Shape Every Design

You don't need exact figures, but you do need the orders of magnitude, because they decide which designs are even possible. These are rough, typical values — real numbers vary with hardware and network, but the ratios between them are what matter:

approximate latencies (orders of magnitude, not benchmarks)
  Main memory reference                          ~100 ns
  Read 1 MB sequentially from memory             ~10 µs     (microseconds)
  Random read from a fast NVMe SSD               ~20-100 µs
  Round trip inside one datacenter               ~0.5 ms    (500 µs)
  Read 1 MB sequentially from SSD                ~0.5-1 ms
  Disk seek on a spinning HDD                    ~5-10 ms
  Round trip, same continent                     ~20-50 ms
  Round trip, across an ocean                    ~100-200 ms

  1 ms = 1,000 µs = 1,000,000 ns
  A datacenter round trip costs about as much as 5,000 memory reads.

The practical consequence: the number of sequential network round trips is usually what dominates the response time of a distributed request, not the CPU work. A quick back-of-the-envelope calculation makes this concrete:

chatty vs. batched — python
RTT_SAME_DC  = 0.0005   # 0.5 ms
RTT_CROSS_DC = 0.150    # 150 ms

items = 100

# Fetch each item with its own sequential request
print(f"chatty, same DC:    {items * RTT_SAME_DC * 1000:.0f} ms")   # 50 ms
print(f"chatty, cross-DC:   {items * RTT_CROSS_DC:.1f} s")         # 15.0 s

# Fetch all 100 in one batched request
print(f"batched, same DC:   {RTT_SAME_DC * 1000:.1f} ms")          # 0.5 ms
print(f"batched, cross-DC:  {RTT_CROSS_DC * 1000:.0f} ms")         # 150 ms
Where this shows up later

Consensus algorithms (Module 3) need at least one round trip to a majority of nodes per write. That's why a Raft cluster spread across three continents has write latency in the hundreds of milliseconds — physics, not a slow implementation.

5. The Core Trade-offs (and the Course Map)

Almost every design decision in distributed systems trades off between three things you would like to have all at once:

  • Consistency — every reader sees the same, up-to-date data, as if there were only one copy.
  • Availability — every request gets a response, even when some machines or links are down.
  • Latency — responses come back fast, without waiting on far-away machines.

You can't maximize all three while the network can fail. Keeping copies perfectly consistent requires coordination (round trips, so latency), and coordination is impossible across a broken link (so you lose availability on one side). Week 8 makes this precise with CAP and PACELC; for now, keep the tension in mind, because every module is a different way of managing it:

6. Hands-on Exercise

Hands-on

Simulate an unreliable network and audit a real system for the fallacies

Get a feel for partial failure with your own eyes before we formalize it next week.

Part 1 — A flaky remote call:

  1. Write a function remote_increment(counter) that simulates a network call: with 10% probability drop the request (do nothing), with 10% probability perform the increment but "lose" the reply, and otherwise perform it and return normally. Use time.sleep(random.uniform(0, 0.05)) for latency. Model a lost message by raising a TimeoutError.
  2. Call it 1,000 times from a client that simply retries on TimeoutError until it succeeds.
  3. Compare the counter's final value with 1,000. Explain the difference using the six cases from Section 2.
Hint

The counter will end up higher than 1,000. Every "reply lost" timeout causes a retry of an increment that already happened. Hold on to this program: Week 4 fixes it with idempotency keys.

Part 2 — Fallacy audit:

  1. Pick a system you know (a project of your own, a work service, or a well-known app you can sketch).
  2. Draw its main components and the network arrows between them.
  3. For at least three arrows, write down which fallacy would hurt most there, and what currently happens if that link is slow or down.

Part 3 — Back of the envelope:

  1. A page load makes 12 sequential calls to a service in another region (RTT 120 ms). Estimate the network-only latency.
  2. Propose two changes that would cut it by at least 10×.

7. Knowledge Check

5 quick questions. Expand each to check your answer.

Q1

What is "partial failure," and why doesn't it occur in the same way in a single-machine program?

Partial failure means some components of the system fail while others keep running, and the running ones often can't tell what failed. A single-machine program typically either works or crashes as a whole, so failure is total and obvious. In a distributed system, failure is partial and ambiguous.

Q2

Node A sends a request to node B and the call times out. Can A safely conclude that B did not perform the operation?

No. A timeout only means A didn't get a reply in time. The request might have been lost, but B might also have processed it and then crashed, or processed it and had the reply lost, or still be processing it slowly. A timeout means "unknown," not "failed."

Q3

Why does the number of sequential round trips usually matter more than CPU time for a distributed request's latency?

A round trip within a datacenter costs around 0.5 ms (and across regions 100 ms or more), while typical CPU work for a request is often microseconds. Sequential calls add their round trips together, so 100 chatty calls cost 100 round trips. Batching or parallelizing the calls removes most of that cost.

Q4

Give two of the eight fallacies of distributed computing and a concrete failure each one causes.

For example: "the network is reliable" leads to code with no timeouts or retries, which hangs forever or silently loses writes when a packet drops. "Topology doesn't change" leads to hard-coded IP addresses that break when a service is redeployed, autoscaled or fails over. Any two fallacies with a matching consequence are a correct answer.

Q5

Why can't a system that keeps multiple copies of data have perfect consistency, availability and low latency all at the same time?

Perfect consistency requires the copies to coordinate before answering, and coordination costs network round trips (latency). When the network between copies is broken, they can't coordinate at all, so the system must either refuse requests (losing availability) or answer with possibly stale data (losing consistency).
