Week 2: Networks, Failures & System Models

Last week showed that things go wrong. This week pins down exactly what can go wrong, because a distributed algorithm is only as good as the failures it was designed for. You'll see why networks delay and drop messages, why no failure detector can be perfect, the standard vocabulary for describing faults and timing, and the distinction between safety and liveness that every algorithm in Module 3 depends on.

Module 1 of 5 Week 2 of 16 ~3 Hours Hands-on Exercise Included

By the end of this week, you'll be able to

  • Explain why a failure detector cannot distinguish a slow node from a dead one
  • Classify a system's assumptions using fault models (crash-stop, crash-recovery, Byzantine) and timing models
  • Tell safety properties apart from liveness properties, and say which one an algorithm must never violate

1. Why Networks Are Unreliable

Datacenter networks are asynchronous packet networks: a node sends a packet and the network makes a best effort to deliver it, with no upper bound on how long that takes. TCP adds retransmission and ordering on top, but it can't make a dead link alive, and when it gives up you're back to an ambiguous timeout.

Delays come from far more places than cables being cut:

where a "network delay" actually comes from
  sender                                                     receiver
  ┌──────────────┐   ┌────────┐   ┌────────┐   ┌──────────────────────┐
  │ app → OS     │──▶│ switch │──▶│ switch │──▶│ NIC → OS queue → app │
  │ send buffer  │   │ queue  │   │ queue  │   │                      │
  └──────────────┘   └────────┘   └────────┘   └──────────────────────┘
        ▲                ▲            ▲                  ▲
  CPU busy,         congestion:   a full queue      app paused by a
  VM paused by      queues grow,  DROPS packets;    GC pause, swap,
  the hypervisor    latency grows TCP retransmits   or a busy event loop

A network partition is the extreme case: some nodes can talk to each other but not to others — for example, a switch failure splits a five-node cluster into a group of three and a group of two. Each side is healthy, can serve its own clients, and can't see the other. Partitions are not hypothetical: large-scale studies of production networks report them regularly, caused by hardware faults, misconfigurations and software upgrades.

A paused process looks exactly like a network failure

A stop-the-world garbage-collection pause of a few seconds, or a VM being live-migrated, freezes a process completely. To everyone else it looks dead — and when it wakes up, it carries on as if no time had passed, possibly acting on information ("I am the leader") that went stale while it was frozen. Week 11's fencing tokens exist exactly for this.

2. Timeouts & Failure Detection

Because the network gives no delivery deadline, the only tool a node has for deciding "that node is dead" is a timeout. The most common form is a heartbeat failure detector: every node periodically sends "I'm alive" messages, and peers suspect any node they haven't heard from within some timeout.

a minimal heartbeat failure detector — python
import time

class HeartbeatDetector:
    def __init__(self, timeout_s: float):
        self.timeout_s = timeout_s
        self.last_seen: dict[str, float] = {}

    def heartbeat(self, node: str) -> None:
        # Monotonic clock: never use wall-clock time to measure intervals (Week 3)
        self.last_seen[node] = time.monotonic()

    def suspected(self) -> list[str]:
        now = time.monotonic()
        return [n for n, t in self.last_seen.items()
                if now - t > self.timeout_s]

Notice the word suspected, not dead. Choosing the timeout is a genuine trade-off with no right answer:

the timeout dilemma
SHORT TIMEOUT                           LONG TIMEOUT
+ real failures detected quickly        + few false alarms
- slow-but-alive nodes declared dead    - real failures take long to notice
- false failover: work moves, load      - users wait (or get errors) for the
  rises on survivors, more nodes          whole timeout before recovery starts
  look slow -> cascading failure

Production systems often go further than a fixed threshold. The phi accrual failure detector (used by Cassandra and Akka) keeps a history of heartbeat arrival intervals and outputs a continuous suspicion level, letting each component pick how confident it needs to be before acting. It adapts to a network that is normally jittery instead of firing on every blip.

Perfect failure detection is impossible

In an asynchronous network, any failure detector can be wrong in both directions: it can suspect a live node, and it can take arbitrarily long to suspect a dead one. Good distributed algorithms are designed to stay correct even when the failure detector is wrong — it may only cost them speed.

3. Fault Models: What Kind of Failure?

An algorithm's guarantees only hold for the faults it was designed to tolerate, so papers and docs state a fault model up front. From most to least benign:

node fault models
CRASH-STOP      A node works correctly until it halts, then never returns.
                Simplest to reason about; rarely true in practice.

CRASH-RECOVERY  A node may crash and later restart. Anything in memory is
                lost; anything written to stable storage (fsync'd disk)
                survives. This is the model Raft & most databases assume.

OMISSION        A node may fail to send or receive some messages but
                otherwise behaves correctly (e.g. an overloaded NIC).

BYZANTINE       A node may do ANYTHING: send wrong data, lie, send
                different answers to different peers, act maliciously.

Tolerating faults has a price measured in replicas. To keep working with up to f faulty nodes, crash-tolerant consensus (Paxos, Raft) needs 2f + 1 nodes — a majority must survive. Byzantine fault tolerance needs 3f + 1 nodes and far more messages, because honest nodes must outvote liars who may tell each of them a different story.

how many nodes for f failures?
  tolerate f =        1      2      3
  crash faults        3      5      7     (2f + 1)
  Byzantine faults    4      7     10     (3f + 1)
Which model should you assume?

Inside one organization's datacenter, systems usually assume crash-recovery and treat bugs and corruption with checksums rather than full Byzantine tolerance. Byzantine fault tolerance matters when participants don't trust each other — blockchains, some aerospace and safety-critical systems, and cross-organization protocols.

4. Timing Models: How Long Can Things Take?

Alongside faults, an algorithm states what it assumes about timing — how long messages and computation may take:

  • Synchronous — there are known upper bounds on message delay, processing time and clock drift. Algorithms are easy to design here, but real networks don't offer it.
  • Asynchronous — no timing assumptions at all; a message may take any finite amount of time. The safest model, but (as Week 9's FLP result shows) some problems, including consensus, become impossible to solve deterministically in it.
  • Partially synchronous — the system behaves asynchronously for unbounded periods, but eventually there are stretches where bounds hold. This is the realistic model: networks are usually well-behaved, with occasional bad periods.

Paxos and Raft are designed for partial synchrony: they never return a wrong answer during the bad periods, and they make progress again once things calm down. That combination is captured precisely by the next idea.

5. The Two Generals Problem

Two armies camp on opposite sides of a valley and will win only if they attack at the same time. They can communicate only by messengers who must cross the valley and may be captured. General A sends "attack at dawn." Should A attack? Only if B got the message — so B sends back an acknowledgement. But B can't be sure the acknowledgement arrived, so A must acknowledge the acknowledgement, and so on forever.

no finite number of messages ever settles it
  A ── "attack at dawn" ──────────▶ B     B knows. A doesn't know B knows.
  A ◀──────────────── "agreed" ──── B     A knows. B doesn't know A knows.
  A ── "got your agreement" ─────▶ B     ...and the last messenger can
                                           always be the one captured.

It's a proof that no protocol can guarantee common knowledge over an unreliable channel: whoever sends the last message never learns whether it arrived. The practical lesson isn't despair — it's design. Real systems stop chasing certainty and instead make operations safe to repeat (Week 4), or accept a bounded risk of disagreement and resolve it later.

6. Safety vs. Liveness

The correctness properties of a distributed algorithm fall into two categories, and the difference between them is one of the most useful ideas in the field:

two kinds of guarantee
SAFETY   — "nothing bad ever happens"
  examples: two nodes never both believe they are leader in the same term;
            a committed write is never lost; a lock is never held twice.
  if violated: you can point to the exact moment it went wrong.
  violations are PERMANENT — you can't undo a double-spend.

LIVENESS — "something good eventually happens"
  examples: a leader is eventually elected; every request eventually
            gets a response.
  if violated: there's no single bad moment, just waiting forever.
  can be RESTORED — a stalled cluster can recover later.

Algorithms for partially synchronous systems make a deliberate choice: safety must hold always, even when the network misbehaves; liveness is only promised once the network behaves. A Raft cluster cut off from its majority stops accepting writes (a liveness loss) rather than risk two leaders accepting conflicting writes (a safety violation).

Use this vocabulary in design reviews

When someone proposes "just fail over to the other node after a timeout," ask: is this protecting liveness at the cost of safety? If the old node was only paused, not dead, you now have two writers. Naming which property each mechanism protects makes those trade-offs explicit.

7. Hands-on Exercise

Hands-on

Build a heartbeat failure detector and measure its trade-offs

Make the timeout dilemma concrete with real numbers.

Part 1 — Detector and simulated nodes:

  1. Using the HeartbeatDetector from Section 2, simulate 5 nodes that each send a heartbeat every 100 ms, with random network delay drawn from random.expovariate(1 / 0.03) (mean 30 ms, long tail).
  2. Occasionally (1% of beats) inject a "GC pause" that delays a node's next heartbeat by 800 ms. Permanently crash one node partway through the run.

Part 2 — Measure:

  1. Run with timeouts of 200 ms, 500 ms, 1 s and 3 s.
  2. For each, record the number of false suspicions (a live node suspected) and the detection time for the node that really crashed.
  3. Plot or tabulate the results, and choose a timeout you would ship. Justify it in two sentences.
Hint

Keep the simulation single-threaded and drive it with a simulated clock (a variable you advance), rather than real sleeps. You'll get reproducible results in milliseconds instead of minutes, which previews the deterministic-simulation testing technique from Week 15.

Part 3 — Classify a real system:

  1. Pick a database or coordination service you use (PostgreSQL with replicas, Redis Sentinel, etcd, Kafka...). From its docs, find what fault and timing assumptions it makes, and how it detects failure.
  2. Name one safety property and one liveness property it promises.

8. Knowledge Check

5 quick questions. Expand each to check your answer.

Q1

Why can't a heartbeat failure detector ever be perfectly accurate in a real datacenter network?

The network has no upper bound on delay, and processes can pause (GC, VM migration). A missing heartbeat could mean the node is dead, the heartbeat is delayed, or the node is temporarily paused. Any timeout will sometimes suspect live nodes, and a longer timeout only makes detecting real failures slower.

Q2

How many nodes does crash-tolerant consensus need to survive 2 simultaneous failures? How many for 2 Byzantine failures?

Crash faults need 2f + 1 = 5 nodes, so a majority of 3 survives. Byzantine faults need 3f + 1 = 7 nodes, because honest nodes must outvote faulty ones that may send each peer different information.

Q3

What is the difference between the crash-stop and crash-recovery fault models, and why does crash-recovery matter for databases?

In crash-stop, a crashed node never returns. In crash-recovery, it can restart, losing in-memory state but keeping whatever it durably wrote to stable storage. Databases and Raft assume crash-recovery, which is why they must fsync critical state (like votes and log entries) before acknowledging it.

Q4

What does the Two Generals problem prove, and what do practical systems do about it?

It proves that no protocol can guarantee agreement (common knowledge) over a channel that can lose messages, because the sender of the last message can never know it arrived. Practical systems accept this and design operations to be safe to retry (idempotency), or tolerate and later reconcile rare disagreements.

Q5

A Raft cluster loses contact with its majority and stops accepting writes. Is that a safety or a liveness issue, and why is that the right trade?

It's a liveness loss: the system isn't making progress, but nothing incorrect has happened, and progress resumes when connectivity returns. The alternative, accepting writes on both sides of a partition, risks a safety violation (conflicting committed writes) that can never be undone.
