Week 11: Coordination: Leases, Locks & Fencing

Consensus (Weeks 9–10) is expensive enough that most systems don't implement it themselves — they outsource it to a small, dedicated coordination service and build everything else, from leader election to service discovery, on top. This week covers what those services are for, why a "distributed lock" is far more dangerous than it sounds, and the one mechanism — fencing — that makes coordination safe anyway.

Module 3 of 5 Week 11 of 16 ~3 Hours Hands-on Exercise Included

By the end of this week, you'll be able to

  • Explain what a coordination service like ZooKeeper or etcd is for, and why it isn't a general-purpose database
  • Describe the process-pause problem that makes a plain distributed lock dangerous
  • Use a fencing token to make a lease safe even when a holder pauses past its expiry
  • Build leader election and service discovery on top of a coordination service's primitives

1. ZooKeeper & etcd as Coordination Primitives

Running Paxos or Raft correctly is hard enough that most engineering teams don't implement consensus themselves — they delegate it to a small, highly available, strongly consistent key-value store purpose-built for coordination, such as ZooKeeper (which uses its own Raft-like protocol, Zab) or etcd (built directly on Raft). Everything else in the system builds on a handful of small primitives these services expose:

  • Strongly consistent reads/writes on small keys (znodes in ZooKeeper, keys in etcd) — the consensus layer from Weeks 9–10, already solved.
  • Ephemeral entries that automatically disappear when the client that created them disconnects or its session expires.
  • Watches that notify a client the instant a key or directory changes, instead of making it poll.

These services are deliberately not a general-purpose database: they're optimized for a small amount of frequently-read, latency-sensitive metadata (who's the leader, what's the current config, which services are alive) rather than bulk application data. Storing megabytes of data or routing high write throughput through one is a well-known way to bring down the exact system every other service depends on to coordinate.

A coordination service is a single point of coordination, not a single point of failure

It runs as its own small Raft/Zab cluster (typically 3 or 5 nodes) specifically so that it survives the same node failures everything else needs to tolerate — the irony of a "highly available coordination service" being itself a single machine would defeat the entire point.

2. Leases & Why Distributed Locks Are Dangerous

A naive distributed lock — "whoever creates this key first holds exclusive access" — looks safe but has a serious gap: what happens if the holder stalls? A garbage-collection pause, a hypervisor migration, or just a slow disk write can freeze a process for seconds without killing it. The process still believes it holds the lock; meanwhile the coordination service, seeing no heartbeat, has already given the lock to someone else.

the process-pause problem
t=0   Node A acquires the lock, begins writing to shared storage
t=1   Node A hits a long GC pause — frozen, not crashed
t=2   Lock's lease expires (no heartbeat) — coordination service frees it
t=3   Node B acquires the SAME lock, begins writing to shared storage
t=4   Node A wakes up from its pause — STILL BELIEVES it holds the lock,
      and resumes writing too

→ A and B are now writing to the same shared resource AT THE SAME TIME,
  each convinced it has exclusive access.

A lease makes this gap explicit instead of hiding it: a lock granted with a bounded time-to-live that the holder must actively renew before it expires. A lease doesn't prevent the scenario above — it only guarantees the coordination service's side of the bookkeeping is honest about how long a grant is valid for. Making the underlying resource itself safe needs one more piece.

3. Fencing Tokens

A fencing token is a number that increases every time the lock or lease changes hands, issued by the coordination service alongside the grant. The holder must include this token with every write it sends to the protected resource — and the resource itself (not the coordination service) is responsible for rejecting any write tagged with a token lower than the highest one it has already seen.

the same scenario, now fenced — python-style pseudocode
# coordination service hands out a token with every lease grant
lease_a = coordinator.acquire_lock("job-x")          # token = 33
# ... Node A pauses ...
lease_b = coordinator.acquire_lock("job-x")          # token = 34 (A's lease expired)

# the SHARED RESOURCE enforces the fencing, not the coordinator
def storage.write(data, token):
    if token < storage.highest_token_seen:
        raise StaleTokenError()                      # A's write (token=33) REJECTED
    storage.highest_token_seen = token
    storage.apply(data)

# Node B's write (token=34) succeeds; Node A's late write (token=33) is
# rejected by the storage layer itself — the lock's exclusivity is now
# enforced by the resource, not by trusting that only one node thinks
# it's the holder.

This should feel familiar: it's the exact same idea as Week 5's epoch numbers for safe leader failover, generalized from "reject a stale leader's writes" to "reject any stale lock holder's writes," enforced at the resource itself rather than relying on the coordinator's say-so.

A lease without a fencing check at the resource is not actually safe

Checking "is my lease still valid?" on the client side right before writing does not help — the pause can happen in the gap between that check and the write landing. The check that matters is the one the resource itself performs when the write arrives.

4. Leader Election & Service Discovery on Top

With leases and fencing in place, two more Week 5–7 problems become straightforward to build on top of a coordination service instead of hand-rolling:

  • Leader election: every candidate races to create the same ephemeral key (or znode); whichever one succeeds is the leader until its session ends, at which point the key disappears and the remaining candidates race again. No custom RequestVote protocol needed when the coordination service's own consensus already handles the race correctly.
  • Service discovery: each service instance registers an ephemeral entry under a well-known path on startup, and disappears automatically if it crashes or loses its session. Clients set a watch on that path instead of polling a static config file or load balancer, and are notified the moment the set of healthy instances changes.

Both are the same pattern: let the coordination service's consensus and ephemeral keys do the hard part, and build everything else as a thin client around watches and fenced leases.

5. Hands-on Exercise

Hands-on

Build a toy lock service, then prove fencing catches what a lease alone misses

Part 1 — Leases without fencing:

  1. Build an in-memory "lock service" that grants a lease on a named lock with a TTL, releasing it automatically once the TTL expires without renewal.
  2. Build a shared "storage" object that any lease holder can write to, with no checks at all.
  3. Simulate a holder that acquires the lease, then pauses (just sleep past the TTL) before writing. Acquire the same lease from a second simulated client in the meantime, and have both eventually write. Confirm both writes land — the corruption scenario from Section 2.

Part 2 — Add fencing tokens:

  1. Have the lock service issue a monotonically increasing token with every lease grant.
  2. Add a highest_token_seen check to the storage object's write method, exactly as in Section 3's pseudocode.
  3. Re-run Part 1's exact scenario and confirm the paused holder's stale write is now rejected, while the second client's write succeeds.

Part 3 — Leader election on top:

  1. Using the same lock service, have 3 simulated candidates race to acquire a lock named "leader".
  2. Have the winner hold it (renewing before each TTL) until you manually force it to stop renewing; confirm one of the remaining candidates acquires it next.
Hint

Make sure the fencing check in Part 2 lives on the storage object, not on the lock service. A check on the lock service only tells a client whether it currently holds a valid lease — it can't stop a write that's already in flight by the time the lease expires.

6. Knowledge Check

5 quick questions. Expand each to check your answer.

Q1

Why shouldn't a coordination service like ZooKeeper or etcd be used to store bulk application data?

It's optimized for a small amount of frequently-read, latency-sensitive coordination metadata, not bulk data or high write throughput. Overloading it that way risks bringing down the exact service every other system depends on for coordination.

Q2

Describe the process-pause problem that makes a plain distributed lock dangerous.

A holder can stall (GC pause, hypervisor migration, slow disk) long enough for its lease to expire and be granted to another node, without the original holder realizing it has lost the lock. When it wakes up, it still believes it holds exclusive access, and both nodes can end up writing to the shared resource at once.

Q3

What does a fencing token guarantee, and which component is responsible for enforcing it?

It guarantees that a write from a stale lock holder (carrying an older token) is rejected, even if that holder still believes it's the valid owner. The shared resource itself enforces this, by rejecting any write whose token is lower than the highest one it has already accepted — not the coordination service.

Q4

Why doesn't checking "is my lease still valid?" on the client immediately before writing make a lease safe on its own?

A pause can happen in the gap between that check succeeding and the write actually landing at the resource, so the check can pass and the lease can still expire before the write arrives. Only a check performed by the resource itself, at the moment the write arrives, closes that gap.

Q5

How does leader election work when built on top of a coordination service's ephemeral keys?

Every candidate races to create the same ephemeral key; whichever one succeeds becomes leader. That key automatically disappears if the leader crashes or its session ends, at which point the remaining candidates race to create it again — all without implementing a custom voting protocol.
