Week 9: Consensus, FLP & Paxos

Every "elect a new leader" and "agree on the next log entry" from earlier weeks was quietly assuming a majority of nodes could agree on a single value even while some of them fail or run slow. This week names that problem — consensus — and takes it seriously: a 1985 result proving it's impossible to solve perfectly, and Paxos, the algorithm that solves it anyway by relaxing exactly the right guarantee.

Module 3 of 5 Week 9 of 16 ~3.5 Hours Hands-on Exercise Included

By the end of this week, you'll be able to

  • State the consensus problem's three required properties precisely
  • Explain what the FLP impossibility result actually proves, and why real systems aren't stuck anyway
  • Walk through single-decree Paxos's two phases and explain why each step is necessary
  • Describe how Multi-Paxos turns repeated consensus into a replicated state machine

1. The Consensus Problem

Consensus asks a set of nodes to agree on a single value, even though some of them may crash or run slow, and even though the network between them can lose or delay messages (Week 2). A correct consensus algorithm must guarantee three properties at once:

  • Agreement: no two correct nodes ever decide on different values.
  • Validity: the decided value must be one that some node actually proposed — a protocol can't just invent an answer.
  • Termination: every correct node eventually decides something.

This single problem is quietly underneath nearly everything from Weeks 5–8: picking a new leader during failover without two leaders disagreeing (Week 5), and deciding the one true next entry in a replicated log so every replica ends up with the exact same history (the replicated-state-machine idea Section 4 returns to). Solve consensus once, correctly, and a huge amount of earlier hand-waving — "a quorum-based tool decides" from Week 5 — gets a real algorithm underneath it.

2. The FLP Impossibility Result

In 1985, Fischer, Lynch and Paterson proved something uncomfortable: in a fully asynchronous network (no bound at all on message delay) with even one faulty process, no deterministic consensus algorithm can guarantee all three properties — agreement, validity, and termination — every time. This is now called the FLP impossibility result.

The intuition traces straight back to Week 2's core fallacy: in a truly asynchronous model, a message that hasn't arrived yet is indistinguishable from a message that never will. A correct algorithm can always be forced into a state where it can't yet tell whether a slow node is about to respond or has crashed — and FLP shows an adversary can keep exploiting exactly that ambiguity forever, making the algorithm wait indefinitely without ever violating agreement or validity. It's not a question of a smarter algorithm; it's a proof that total asynchrony plus one failure is fundamentally too little information to guarantee a decision.

why real systems aren't actually stuck
FLP's model:        fully asynchronous — NO bound on message delay, ever.

Paxos/Raft's model: PARTIALLY synchronous — delays are usually bounded in
                     practice, even though no fixed bound is guaranteed.
                     They use randomized or adaptive timeouts (Week 10) to
                     make progress most of the time, while FLP guarantees
                     they can never promise termination with 100% certainty
                     in the worst case.

the trade actually made:  give up "always terminates" (impossible anyway),
                           keep agreement and validity ALWAYS, and terminate
                           "with overwhelming probability in practice."

This is why Paxos and Raft never claim to beat FLP — they don't need to. They keep agreement and validity as absolute guarantees under any conditions, and accept that termination is only guaranteed once the network behaves reasonably (the partial-synchrony assumption), which real networks do the overwhelming majority of the time.

FLP is a reason to be suspicious of "it always terminates" claims

Any protocol advertising guaranteed termination under pure asynchrony with faulty nodes is either wrong, or secretly relying on a timing assumption it isn't stating. Knowing FLP means knowing exactly which corner is being cut, instead of being surprised by it in production.

3. Single-Decree Paxos, Step by Step

Paxos solves consensus for one agreed value (a "decree") using three logical roles — a node often plays more than one: proposers suggest values, acceptors vote on them, and learners find out the result. Paxos runs in two phases, and the key trick is that phase 1 doesn't commit to a value yet — it only reserves the right to propose one.

phase 1 — prepare / promise
proposer picks a proposal number n (must be higher than any it's used before)
proposer sends  Prepare(n)  to a MAJORITY of acceptors

each acceptor, on receiving Prepare(n):
  if n > any proposal number it has already promised:
    promises not to accept any proposal numbered < n
    replies Promise(n, previously_accepted_value_if_any)
  else:
    ignores it (or replies "no")
phase 2 — accept / accepted
once the proposer has Promise replies from a MAJORITY:
  if any reply carried a previously accepted value:
    proposer MUST now propose that value (the highest-numbered one seen)
  else:
    proposer is free to propose its own value
  proposer sends  Accept(n, v)  to that same majority

each acceptor, on receiving Accept(n, v):
  if n >= any proposal number it has promised:
    accepts it:  Accepted(n, v)
  else:
    rejects it

once a MAJORITY has accepted (n, v):  v is CHOSEN — consensus reached

The rule forcing a proposer to re-propose an already-accepted value is what makes Paxos safe: it guarantees that once a majority has accepted a value, every later proposal (by any proposer, even one that didn't know a decision had already happened) is forced to carry that same value forward, rather than overwriting it with something else.

Dueling proposers can stall progress — but never break safety

Two proposers can keep issuing higher and higher proposal numbers, each invalidating the other's in-progress phase 2 before it reaches a majority — a livelock. This is FLP in miniature: termination is never guaranteed. Agreement and validity hold regardless, which is exactly the trade Section 2 described. Randomized backoff between retries (the same idea as Week 4's jittered retries) makes livelock practically rare.

4. Multi-Paxos & the Replicated State Machine

A real system doesn't need to agree on one value once — it needs to agree on an ever-growing sequence of log entries, one per operation. Running full single-decree Paxos (both phases) for every single entry would cost two network round trips per write, every time.

Multi-Paxos optimizes this: run phase 1 once to elect a stable distinguished proposer (in practice, a leader) for a range of log slots. As long as no other proposer interferes, that leader can skip phase 1 for every subsequent slot and jump straight to phase 2 — turning the common case into one round trip per log entry instead of two.

from "agree on one value" to a replicated log
single-decree Paxos:   agree on ONE value, once.

Multi-Paxos:            elect a leader (phase 1, once)
                        leader proposes slot 1's value (phase 2 only)
                        leader proposes slot 2's value (phase 2 only)
                        leader proposes slot 3's value (phase 2 only)
                        ...

every node applies the AGREED log, in order, to its own local state
  → every node ends up in the exact same state
  → this is a REPLICATED STATE MACHINE (RSM)

A replicated state machine is precisely what Week 5's leader-follower replication was informally doing — "agree on an order, then everyone replays it" — except Multi-Paxos now gives that informal idea an actual proof: even if the leader crashes mid-stream, a new leader elected via another phase 1 round can only ever continue the agreed log, never silently rewrite it. Multi-Paxos is powerful but notoriously under-specified in its original presentation; next week's algorithm, Raft, was designed specifically to make this exact idea easy to implement correctly.

5. Hands-on Exercise

Hands-on

Implement single-decree Paxos, then watch it livelock and fix it

Part 1 — Three acceptors, one proposer:

  1. Model 3 acceptors as objects each tracking highest_promised and accepted (n, v).
  2. Implement a single proposer running Prepare then Accept against a majority (2 of 3), and confirm a value gets chosen.

Part 2 — Two competing proposers:

  1. Add a second proposer trying to propose a different value, interleaving its Prepare/Accept calls with the first proposer's.
  2. Have each proposer immediately retry with a higher proposal number whenever an acceptor rejects it. Run this and confirm you can produce a livelock where neither proposer's phase 2 ever reaches a majority.
  3. Add randomized backoff before each retry (Week 4's jittered backoff) and confirm the livelock resolves in a bounded number of attempts across repeated runs.

Part 3 — Extend to a tiny replicated log:

  1. Run single-decree Paxos independently for 5 consecutive slots, with one proposer acting as a stable "leader" that skips phase 1 after the first slot.
  2. Apply the 5 agreed values in order to a toy state machine (e.g. a list each node appends to) on 3 separate "replicas," and confirm all 3 end up byte-for-byte identical.
Hint

Make sure your proposer actually re-proposes the value an acceptor returns in a Promise reply when one exists. Skipping that check is the single most common way to accidentally "re-derive" a protocol that looks like Paxos but no longer guarantees agreement.

6. Knowledge Check

5 quick questions. Expand each to check your answer.

Q1

Name the three properties a correct consensus algorithm must guarantee.

Agreement (no two correct nodes decide different values), validity (the decided value was actually proposed by some node), and termination (every correct node eventually decides).

Q2

What does the FLP result actually prove, and which of the three consensus properties does it threaten?

It proves that in a fully asynchronous network with even one faulty process, no deterministic algorithm can guarantee all three properties every time. Specifically, it threatens termination — agreement and validity can still always be preserved, but guaranteed termination cannot.

Q3

In Paxos's Phase 1, what does an acceptor promise, and what information might it return to the proposer?

It promises not to accept any future proposal numbered lower than the one it just promised. If it has already accepted a value under some earlier proposal number, it returns that value and number to the proposer.

Q4

Why must a proposer re-propose a value it learned about in Phase 1, instead of proposing its own preferred value?

Because that value may already have been (or be about to be) chosen by a majority under an earlier proposal number. Forcing every later proposal to carry the already-accepted value forward is what guarantees agreement — overwriting it with a different value would break consensus.

Q5

How does Multi-Paxos reduce the cost of agreeing on each entry in a growing log, compared to running single-decree Paxos independently for every entry?

It runs Phase 1 once to elect a stable leader for a range of slots. As long as no other proposer interferes, that leader can skip Phase 1 for every later slot and go straight to Phase 2, cutting the common case from two round trips per entry down to one.
