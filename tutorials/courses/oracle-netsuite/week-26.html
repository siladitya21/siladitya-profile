Week 26: Capstone: Build & Ship a Custom SuiteApp

This is it — the week every other week in this course was quietly preparing you for. You're taking the design you wrote in Week 25 and actually building it: a custom record, a SuiteFlow workflow that moves it through a process, a SuiteScript User Event script that enforces logic SuiteFlow can't, a RESTlet that lets an outside system read and write your data, and finally packaging the whole thing as a SuiteApp and deploying it with the SuiteCloud Development Framework (SDF) — the same way real NetSuite consultancies ship customizations to production. By the end, you won't just understand NetSuite. You'll have shipped something on it.

Module 6 of 6 Week 26 of 26 · Capstone ~4 Hours Hands-on Exercise Included

By the end of this week, you'll be able to

  • Wire a custom record, a SuiteFlow workflow and a SuiteScript User Event script into one working automation
  • Expose a RESTlet so an external system can create and query your custom data over HTTP
  • Package every customization into an SDF project and deploy it as a single SuiteApp

1. Custom Record, SuiteFlow Workflow & SuiteScript Working Together

Start by building exactly what you sketched in Week 25: the custom record type (Customization → Lists, Records & Fields → Record Types → New), with every field from your design table added with the exact IDs you chose. This is mechanical if your Week 25 design was specific — if you're hesitating over a field's type here, that's a sign the design pass needs a second look, not a reason to improvise on the fly.

Next, build the SuiteFlow workflow (Week 11) for whatever you assigned to it — most commonly, routing the record through a status field as it's created, reviewed and approved, with a Set Field Value action and an email notification at each transition. Then write the one piece of logic you assigned to SuiteScript instead: typically a User Event beforeSubmit that validates something a workflow can't easily check, like cross-field math or a lookup against another record.

User Event script — beforeSubmit validation (SuiteScript 2.1)
/**
 * @NApiVersion 2.1
 * @NScriptType UserEventScript
 */
define(['N/record', 'N/error'], (record, error) => {

  const beforeSubmit = (context) => {
    if (context.type !== context.UserEventType.CREATE &&
        context.type !== context.UserEventType.EDIT) {
      return;
    }

    const rec = context.newRecord;
    const dueDate = rec.getValue({ fieldId: 'custrecord_el_due_date' });
    const loanDate = rec.getValue({ fieldId: 'custrecord_el_loan_date' });

    if (dueDate && loanDate && dueDate < loanDate) {
      throw error.create({
        name: 'INVALID_DUE_DATE',
        message: 'Due date cannot be before the loan date.'
      });
    }
  };

  return { beforeSubmit };
});
Build and test each layer separately before connecting them

Create the record manually and confirm fields save correctly first. Then deploy the User Event script alone and confirm the validation fires. Only then turn on the workflow. Debugging three new pieces at once is much harder than debugging them one at a time — the same governance-aware, incremental mindset from Week 20.

Once each piece works in isolation, test the full path end to end: create a record that should trigger your validation error, confirm it's rejected; create a valid one and confirm the workflow routes it correctly. That's the core automation finished — everything else this week extends it outward.

2. A RESTlet Exposed for an External Integration

A RESTlet (Week 19) turns your custom record into something an external system can create and query over plain HTTP, authenticated with token-based auth or OAuth 2.0. This is what makes your capstone a real integration point rather than a UI-only feature — exactly the SuiteTalk-adjacent pattern from Week 21, scoped down to a single custom endpoint you own.

Keep the RESTlet's job narrow: a GET to look up records (optionally filtered), and a POST to create one. Each entry point does input validation and returns a plain JSON object — resist the urge to make it "smart"; a RESTlet's value is being a predictable, well-documented door into your data, not a place to bury business logic that belongs in the User Event script you already wrote.

RESTlet — create & query Equipment Loan records (SuiteScript 2.1)
/**
 * @NApiVersion 2.1
 * @NScriptType Restlet
 */
define(['N/record', 'N/search'], (record, search) => {

  const post = (requestBody) => {
    const rec = record.create({ type: 'customrecord_equipment_loan' });
    rec.setValue({ fieldId: 'custrecord_el_employee', value: requestBody.employeeId });
    rec.setValue({ fieldId: 'custrecord_el_asset', value: requestBody.assetId });
    rec.setValue({ fieldId: 'custrecord_el_loan_date', value: new Date(requestBody.loanDate) });
    rec.setValue({ fieldId: 'custrecord_el_due_date', value: new Date(requestBody.dueDate) });
    const id = rec.save();
    return { success: true, id };
  };

  const get = (params) => {
    const results = search.create({
      type: 'customrecord_equipment_loan',
      filters: params.employeeId
        ? [['custrecord_el_employee', 'anyof', params.employeeId]]
        : [],
      columns: ['custrecord_el_asset', 'custrecord_el_due_date', 'custrecord_el_status']
    }).run().getRange({ start: 0, end: 50 });

    return results.map((r) => ({
      id: r.id,
      asset: r.getValue('custrecord_el_asset'),
      dueDate: r.getValue('custrecord_el_due_date'),
      status: r.getText('custrecord_el_status')
    }));
  };

  return { post, get };
});
Deploy the RESTlet with token-based auth, not a shared login

Create an Integration record and an Access Token scoped to a role with only the permissions this RESTlet needs. Testing with a real admin's username/password is a habit to break now — it's exactly the kind of over-broad access Week 10's segregation-of-duties principle warned against.

Test the RESTlet with a tool like Postman: a POST with a sample employee/asset payload should return a new internal ID, and a GET filtered by that employee should return the record you just created. That round trip is your proof the integration layer actually works, independent of the NetSuite UI.

3. Packaging & Deploying the Finished SuiteApp via SDF

Everything so far could have been built by hand, point-and-click, inside a single account. That doesn't scale past one developer or one environment — which is exactly what Week 23's SuiteCloud Development Framework solves. An SDF project captures your custom record, workflow, and scripts as version-controlled source files that deploy identically to any account: your sandbox today, production next week, a client's account next month.

The core SDF workflow is: scaffold a project, import your existing customizations into it (or hand-author the XML/JS from scratch), validate the project against the target account, and deploy. This is the same CLI discipline every NetSuite SuiteApp in the wild is actually built and shipped with.

SDF CLI — scaffold, import, validate, deploy
# 1. Create a new SuiteCloud project
suitecloud project:create --type ACCOUNTCUSTOMIZATION --parentdirectory ./equipment-loan-app

# 2. Set up (or reuse) an authenticated account connection
suitecloud account:setup

# 3. Pull your manually-built customizations into the project as source
suitecloud object:import --type customrecordtype --scriptid customrecord_equipment_loan
suitecloud object:import --type workflow --scriptid customworkflow_equipment_loan
suitecloud file:import --paths "/SuiteScripts/equipment_loan_ue.js" "/SuiteScripts/equipment_loan_restlet.js"

# 4. Validate the whole project against the target account
suitecloud project:validate

# 5. Deploy — bundles every object/file above into one atomic deployment
suitecloud project:deploy
Commit the SDF project to a real git repository

Once your customizations live as files instead of only existing inside the NetSuite UI, version control (Week 23) is what turns "a change someone made once" into a reviewable, revertible history — the same discipline that makes any other software project maintainable.

Deploy first to a sandbox, re-run your end-to-end test from Section 1 and your RESTlet round trip from Section 2 against the freshly-deployed copy, and only then consider the SuiteApp done. That sandbox-first habit, from Week 14, is exactly how real NetSuite teams avoid shipping an untested customization straight to production.

4. Capstone Build

Hands-on · Capstone

Build and ship the SuiteApp you scoped in Week 25

Work from your Week 25 design document part by part. This runs in a real NetSuite account (SuiteTraining or sandbox) and, in the final part, the SuiteCloud IDE/CLI.

Part 1 — Build the record and the workflow:

  1. Create your custom record type with every field from your Week 25 data-model table, using the exact field IDs you designed.
  2. Build the SuiteFlow workflow for the piece of automation you assigned to it, including at least one state transition and one notification.
  3. Create a few test records by hand and confirm the workflow routes them as expected.

Part 2 — Write and deploy the script layer:

  1. Write a User Event script that enforces the validation or logic you assigned to SuiteScript in Week 25, adapting the pattern above to your own fields.
  2. Deploy it to your custom record and confirm it blocks an invalid record and allows a valid one.
  3. Write and deploy a RESTlet with a GET and a POST entry point for your record, authenticated with a scoped token-based-auth integration — not an admin login.
  4. Test both entry points with Postman (or curl) and confirm a full create-then-query round trip works.

Part 3 — Package and deploy with SDF:

  1. Scaffold an SDF project and import your custom record, workflow and script files into it.
  2. Run project:validate and fix anything it flags.
  3. Deploy the project to a sandbox account (or a second role/instance if that's all you have access to) and re-run your Part 1 and Part 2 tests against the deployed copy.
You just shipped a SuiteApp

A custom data model, a no-code workflow, server-side validation, an authenticated external API, and a version-controlled, repeatable deployment — that's the same shape as a production NetSuite customization at a real company. Everything from Week 1's "what is a role" to this RESTlet call is now one connected system you built yourself. Congratulations on finishing the course.

5. Knowledge Check

5 quick questions. Expand each to check your answer.

Q1

Why should you test the custom record, the workflow, and the script separately before testing them together?

If all three are new at once and something fails, you can't tell which layer caused it. Testing each in isolation first — the same incremental, governance-aware mindset from Week 20 — makes the eventual end-to-end test a confirmation, not a debugging session.

Q2

Why does validating the due date against the loan date belong in a User Event script rather than the SuiteFlow workflow?

It's a cross-field comparison with custom error handling at save time — exactly the kind of validation logic Week 25's decision framework assigns to scripting rather than SuiteFlow's field-update-and-approval model.

Q3

Why authenticate the RESTlet with a scoped token-based-auth integration instead of an administrator's login credentials?

An admin login grants far more access than the integration needs, violating the segregation-of-duties principle from Week 10. A token scoped to a narrow role limits the blast radius if the credential is ever exposed, and makes it obvious from the role alone what the integration is allowed to touch.

Q4

What does an SDF project give you that building everything by hand in the NetSuite UI doesn't?

Version-controlled, repeatable deployment: the same customization can be validated and deployed identically to a sandbox, a production account, or a client's account, and the change history lives in git instead of only in someone's memory of what they clicked.

Q5

Why re-run your Part 1 and Part 2 tests again after deploying via SDF to a sandbox, instead of trusting that the deploy worked?

A clean project:validate and deploy confirms the files were accepted, not that the automation behaves correctly in that account. Re-running your end-to-end and RESTlet round-trip tests against the deployed copy is the sandbox-first habit from Week 14 — catching environment-specific issues before anything reaches production.
