Week 3: Custom Fields, Forms & Lists

Week 2 gave you the vocabulary for everything NetSuite ships with out of the box. This week is about the first 80% of "customizing NetSuite" that most administrators ever do — extending that model with custom fields, entirely new custom record types, and reshaped forms — and doing all of it with point-and-click configuration, zero code. Everything here is reversible and low-risk compared to what Module 4 will eventually let you do in SuiteScript, which makes it the right place to build real configuration instincts.

Module 1 of 6 Week 3 of 26 ~3 Hours Hands-on Exercise Included

By the end of this week, you'll be able to

  • Create a custom field scoped to the right record type, and know in advance where it will and won't appear
  • Build a simple custom record type with its own fields to model data NetSuite has no standard record for
  • Customize a transaction form's layout, add a field display rule, and set a preferred form per role

1. Custom Entity, Transaction & Body Fields — and Where Each One Surfaces

Go to Customization → Lists, Records, & Fields → [Field Type] to create any custom field. The field type you pick up front — Custom Entity Field, Custom Transaction Body Field, Custom Transaction Column Field, Custom Item Field, Custom CRM Field, and others — is the single most important decision, because it determines which record types the field is even eligible to appear on. Pick the wrong type and no amount of later configuration will make a field show up where you expected it.

Within most field types, an "Applies To" subtab lets you check exactly which record types (Customer? Vendor? Both?) or transaction types (Sales Order? Invoice? Both?) the field is available on. A Column checkbox on a transaction field decides whether it appears once per header (body) or once per line (sublist column) — this single checkbox is the difference between "one value for the whole order" and "a value for every line item."

deciding which custom field type to use
Does it describe a PERSON or COMPANY (customer, vendor, contact)?
    → Custom Entity Field  (Applies To: Customer / Vendor / etc.)

Does it describe ONE TRANSACTION, header-level (ship instructions, PO reason)?
    → Custom Transaction Field, with "Column" UNCHECKED  → body field

Does it describe EACH LINE on a transaction (discount %, warranty months)?
    → Custom Transaction Field, with "Column" CHECKED    → sublist column

Does it describe a PRODUCT (weight class, hazard flag)?
    → Custom Item Field  (Applies To: Inventory Item / Service Item / etc.)

Two more subtabs matter in daily practice: Sourcing & Filtering lets a field auto-populate from a related record (e.g. pull a customer's default tax code onto every invoice automatically) and controls whether the field can be used as a filter or results column in a saved search — easy to forget, and the most common reason a brand-new custom field "doesn't show up" in a search you just built.

"Available in search/reports" isn't on by default for every field

If a saved search can't find your new custom field, check the field's Sourcing & Filtering subtab before assuming the search is broken — the checkbox that exposes a field to search is separate from the checkbox that makes it visible on the form.

2. Custom Record Types: Building Your Own Data Model

Sometimes no standard record fits what a business actually needs to track — a service contract, an equipment asset, a warranty claim. Customization → Lists, Records, & Fields → Record Types → New lets you define an entirely new record type from scratch, with its own name, ID, and permissions.

Key options when defining a custom record type: Access Type (whether access is controlled by role permission, or left public to anyone who can log in), Allow Numbering (auto-generate a sequential ID per record instead of relying on a name), Include in Search and Show Notes (same idea as the sourcing/filtering checkbox from Section 1), and Hierarchical — which turns on the same parent-child nesting pattern you saw with sub-customers in Week 2, but for your own custom record. Once the record type exists, you add fields to it exactly the way Section 1 described, just scoped to "Custom Record: <your type>" instead of Customer or Sales Order.

a minimal custom record type: "Equipment Asset"
Record Type: Equipment Asset
  ID: customrecord_equipment_asset
  Allow Numbering: Yes  (EA-0001, EA-0002, ...)
  Include in Search: Yes
  Hierarchical: No

Fields (added after creation, scoped to this record type):
  Serial Number     (Free-Form Text)
  Assigned Employee (List/Record → Employee)
  Purchase Date     (Date)
  Warranty Expires  (Date)
  Status            (List/Record → custom list: Active / In Repair / Retired)
Think before enabling Hierarchical or Numbering after records already exist

Both settings change how existing data is identified and related. Decide on them while the record type is new and empty — retrofitting either one onto a custom record type that already has hundreds of real records is far riskier than getting it right up front.

3. Custom Forms: Layout, Field Display Rules & Role-Based Preferences

A form is the layout of fields and subtabs a user sees when creating or editing a given record type — which fields show, in what order, on which subtab, and whether each one is mandatory, read-only, or hidden entirely. Customization → Forms → Transaction Forms (or Entry Forms for non-transaction records) is where you manage them. NetSuite ships a standard form for every record type, and the single most important habit here is: never edit the standard form directly — clone it first, then customize the clone. Standard forms can be reset or overwritten by NetSuite's own release upgrades; a cloned custom form is yours permanently.

Beyond layout, a form can carry field display rules — point-and-click conditional logic like "show the Discount Reason field only when Discount % is greater than 0," with no scripting involved. This is the no-code version of the dynamic field behavior Week 17 (Client Scripts) will eventually cover in SuiteScript; for straightforward show/hide/require logic, a field display rule is simpler, faster to build, and easier for another administrator to maintain later.

Finally, a form can be set as the preferred form for a specific role (and optionally a specific subsidiary), under the form's own setup or via Setup → Company → Preferred Forms. This is how a Sales Rep role can default to a simplified sales order form with half the fields hidden, while an Administrator role sees the full, unrestricted form — same record type, same data, a different experience per job function.

form customization, start to finish
Standard Sales Order form   (never edit directly)
       │
       └─ Clone → "Sales Order - Sales Rep (Custom)"
                    │
                    ├─ Hide: Cost, Margin, internal fields
                    ├─ Field Display Rule:
                    │     IF Discount % > 0
                    │     THEN show "Discount Reason" (required)
                    │
                    └─ Set as Preferred Form for role: Sales Rep
Clone first, every single time

Even a quick one-field tweak should start from "Customize" (which clones) rather than editing the standard form in place. There's no meaningful cost to cloning, and it's the only way to guarantee your changes survive the next NetSuite release.

4. Hands-on Exercise

Hands-on

Extend the data model and reshape a form

Use your SuiteTraining account or sandbox, with an Administrator role.

Part 1 — Add a scoped custom field:

  1. Create a Custom Entity Field (e.g. "Preferred Contact Method", a List/Record or Free-Form Text field) scoped to Customer only.
  2. Open a customer record and confirm the field appears; confirm it does not appear on a Vendor record.
  3. Check its Sourcing & Filtering subtab and enable it for search, then confirm it's selectable as a results column in a new saved search.

Part 2 — Build a custom record type:

  1. Create a simple custom record type (e.g. "Equipment Asset" or your own idea) with Allow Numbering turned on.
  2. Add 3 custom fields scoped to that record type.
  3. Create two records of this type and confirm their auto-generated IDs.

Part 3 — Customize and assign a form:

  1. Clone the standard Sales Order (or any transaction) form.
  2. Hide one field and add one field display rule on the clone.
  3. Set the clone as the preferred form for your own role, then open a new transaction and confirm the layout and rule both apply.

5. Knowledge Check

5 quick questions. Expand each to check your answer.

Q1

You need a field that holds a different discount percentage for every line item on a sales order. Which field type and setting do you need?

A Custom Transaction Field with the "Column" checkbox checked, applied to Sales Order — that makes it a sublist column so it can hold a different value per line, rather than one value for the whole record.

Q2

A new custom field doesn't appear as an option in your saved search's results columns. What should you check first?

The field's Sourcing & Filtering subtab — whether it's enabled for use in search/reports is a separate setting from whether it's visible on the form, and it's the most common reason a new field "goes missing" from a saved search.

Q3

What does enabling "Hierarchical" on a custom record type give you, and why is it risky to turn on after data already exists?

It gives the custom record type the same parent-child nesting pattern used by sub-customers in Week 2. It's risky to add retroactively because it changes how existing records are identified and related, and retrofitting that structure onto records already in use is much harder than defining it correctly before any data exists.

Q4

Why should you always clone a standard form instead of editing it directly?

Standard forms can be reset or overwritten by NetSuite's own release upgrades, so direct edits to them aren't guaranteed to survive. A cloned custom form is entirely yours and isn't touched by those upgrades.

Q5

What's the no-code way to make a field appear only when another field meets some condition, and what later week covers the code-based equivalent?

A field display rule on a custom form. The code-based equivalent — dynamic field behavior driven by JavaScript running in the browser — is covered in Week 17 (Client Scripts).
