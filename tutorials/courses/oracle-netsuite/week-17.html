Week 17: Client Scripts

Everything so far in this module has run on NetSuite's servers, invisible to the person actually filling out a form. Client Scripts are the opposite: code that runs in the user's own browser, reacting the instant a field changes, before a single byte is sent back to NetSuite. That makes them perfect for responsive, interactive UI behavior — and exactly the wrong place to put anything that has to be guaranteed to happen, since a client script simply never runs outside an interactive form.

By the end of this week, you'll be able to

  • Use pageInit, fieldChanged, saveRecord and validateField for the right job each
  • Implement client-side validation and dynamic, condition-based field behavior
  • Explain precisely where the line between client and server scripting falls, and why it matters for data integrity

1. pageInit, fieldChanged, saveRecord & validateField

A Client Script interacts with the record currently open in the browser through the N/currentRecord module, and exposes entry points tied to concrete user actions rather than server-side lifecycle events:

Client Script skeleton
/**
 * @NApiVersion 2.1
 * @NScriptType ClientScript
 */
define(['N/currentRecord'], function (currentRecord) {

  function pageInit(context) {
    // Runs once, when the form finishes loading (new or existing record).
  }

  function fieldChanged(context) {
    // Runs every time a field's value changes, before it's committed.
    // context.fieldId, context.sublistId, context.line tell you which one.
  }

  function validateField(context) {
    // Runs as a single field commits. Return false to reject just that value.
    return true;
  }

  function saveRecord(context) {
    // Runs when the user clicks Save. Return false to block the entire save.
    return true;
  }

  return {
    pageInit: pageInit,
    fieldChanged: fieldChanged,
    validateField: validateField,
    saveRecord: saveRecord
  };
});

pageInit is where you set sensible defaults or read the initial state of the form. fieldChanged fires constantly as the user works and is the right place for reactive UI updates — recalculating a derived field, say. validateField is narrower: it gates a single field's value as it commits, separate from the broader, whole-record gate that saveRecord provides right before the record actually saves.

saveRecord must return a boolean, not throw

The entry point's contract is explicit: return false to block the save (typically after showing the user an alert() explaining why), or true/nothing to let it proceed. An uncaught error inside it can leave the UI in a confusing half-blocked state.

2. Client-Side Validation & Dynamic Field Behavior

The most common Client Script pattern is conditional field behavior: showing, hiding, enabling or requiring one field based on another's value, entirely as the user types — no page refresh required.

disabling a field based on a dropdown, in fieldChanged
function fieldChanged(context) {
  if (context.fieldId !== 'custbody_delivery_method') return;

  var rec = currentRecord.get();
  var method = rec.getValue({ fieldId: 'custbody_delivery_method' });
  var trackingField = rec.getField({ fieldId: 'custbody_tracking_number' });

  // Only require/enable a tracking number for shipped orders.
  trackingField.isDisabled = (method !== 'SHIPPED');
  if (method !== 'SHIPPED') {
    rec.setValue({ fieldId: 'custbody_tracking_number', value: '' });
  }
}

function validateField(context) {
  if (context.fieldId !== 'custbody_tracking_number') return true;

  var rec = currentRecord.get();
  var method = rec.getValue({ fieldId: 'custbody_delivery_method' });
  var tracking = rec.getValue({ fieldId: 'custbody_tracking_number' });

  if (method === 'SHIPPED' && !tracking) {
    alert('A tracking number is required once delivery method is Shipped.');
    return false;
  }
  return true;
}

currentRecord.get() hands back the live record object the user is editing — the same getValue/setValue/getField API you already used server-side in Week 16, just pointed at the browser's copy of the record instead of a server-loaded one.

fieldChanged can fire recursively if you're not careful

Calling setValue on a field inside its own fieldChanged handler re-triggers fieldChanged for that field. Guard with a check ("only act if the new value differs from what triggered this") the same way Week 16 guarded against User Event recursion.

3. Client vs. Server Scripting: What Each Can and Can't Do

A Client Script only exists while a human has a form open in a browser tab. It never runs during a CSV import, a web services call, a Scheduled Script, a mass update, or a Suitelet request that doesn't explicitly attach one. That single fact has a hard consequence: any validation that matters for data integrity must also exist server-side — typically in a User Event script's beforeSubmit — because a Client Script is, structurally, optional UI polish, not a security boundary.

the entry-path reality
ENTRY PATH                     CLIENT SCRIPT RUNS?   USER EVENT SCRIPT RUNS?
User typing in the UI form      YES                    YES
CSV Import                      NO                      YES
SuiteScript (record.save)       NO                      YES
REST / SOAP web services        NO                      YES
Mass Update                     NO                      YES

In practice, the right split is: Client Scripts give the user fast, friendly feedback while they're typing (so they don't waste time filling out a whole form only to be rejected at the end); User Event scripts guarantee the data is actually correct no matter how it arrived. Neither one replaces the other.

Treat client-side validation as a courtesy, not a guarantee

If duplicating a validation rule on both sides feels redundant, that redundancy is the point — it's exactly how a resilient system avoids depending on a single, bypassable entry path.

4. Hands-on Exercise

Hands-on

Build conditional fields, then prove why a server check still matters

Part 1 — Client-side behavior:

  1. On a custom record or Sales Order, add two custom fields similar to the example (a delivery-method select and a tracking-number text field).
  2. Write and deploy a Client Script implementing the fieldChanged/validateField pattern above.
  3. Confirm in the UI that selecting "Shipped" enables the tracking field and requires it, and that other values clear and disable it.

Part 2 — Prove the gap:

  1. Build a small CSV with a record set to "Shipped" and no tracking number, and import it.
  2. Confirm the import succeeds despite the "required" rule — because the Client Script never ran.

Part 3 — Close the gap:

  1. Add a beforeSubmit User Event script (Week 16) enforcing the same rule server-side, and re-run the CSV import to confirm it's now rejected or corrected.

5. Knowledge Check

5 quick questions. Expand each to check your answer.

Q1

What's the key architectural difference between where a Client Script runs and where a User Event script runs?

A Client Script runs in the user's browser, only while an interactive UI form is open. A User Event script runs server-side, on save, regardless of whether that save came from the UI, a CSV import, web services, or another script.

Q2

What's the difference between fieldChanged and validateField?

fieldChanged fires after a field's value has already changed, and is used for reactive UI updates. validateField fires as a field's value commits and can return false to reject just that field's value, blocking the commit.

Q3

Why must saveRecord return a boolean rather than throw an error to block a save?

That's the entry point's defined contract — the platform checks the returned value (false blocks the save, true/undefined allows it) rather than catching an exception, so an uncaught error can leave the UI in an inconsistent state instead of cleanly blocking the save.

Q4

Give a concrete scenario where a Client Script's validation would never fire at all.

Any non-UI entry path: a CSV import, a REST/SOAP web services call, another SuiteScript calling record.save(), or a mass update — none of these open the interactive form the Client Script is attached to.

Q5

Why is duplicating a validation rule on both the client and server side not actually wasted effort?

Each one does a different job: the client-side copy gives the user fast, friendly feedback while filling out the form; the server-side copy (typically in beforeSubmit) is the only one that actually guarantees the rule holds no matter which entry path created or edited the record.
