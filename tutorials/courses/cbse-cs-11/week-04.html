Chapter 4: Introduction to Problem Solving

Based on NCERT's Class XI Computer Science textbook. Before any Python code, this chapter teaches how to think like a programmer: the four steps of problem solving, what makes a good algorithm, representing one as a flowchart or pseudocode, the three flow-of-control patterns (sequence, selection, repetition), how to verify and compare algorithms, and finally decomposing a complex problem into manageable sub-problems.

Chapter 4 of 11 NCERT pp. 61–86 ~3–4 Hours Exercise Included

By the end of this chapter, you'll be able to

  • Write pseudocode and draw a flowchart for a given problem, identifying input/process/output
  • Use selection (IF/ELSE) and repetition (WHILE) constructs correctly in pseudocode
  • Dry-run an algorithm against edge cases to catch bugs before coding it

4.1–4.2 Steps for Problem Solving

Computers can't solve a problem on their own — precise step-by-step instructions must be given. Success depends on correctly defining the problem, designing a solution (algorithm), then implementing it (program).

The four-step cycle
1. ANALYSING THE PROBLEM
   Read the statement carefully -- identify required INPUT and
   desired OUTPUT before attempting a solution.

2. DEVELOPING AN ALGORITHM
   Devise the solution in natural language first (the algorithm) --
   like a well-written recipe. Keep refining until it covers every
   aspect of the desired solution.

3. CODING
   Convert the finalised algorithm into a programming language.
   Document the procedure for future reference.

4. TESTING AND DEBUGGING
   Check the program meets requirements, runs in acceptable time,
   and gives correct output for ALL possible inputs. Fix logical
   errors found; repeat until clean. (GIGO: Garbage In, Garbage Out
   -- output correctness depends entirely on input correctness.)

4.3 Algorithm

A finite sequence of steps that, if followed correctly, produces the desired output in finite time. Has a definite beginning and end.

4.3.1(A) — Five characteristics of a GOOD algorithm
PRECISION    each step is precisely/exactly stated
UNIQUENESS   each step's result depends only on the input and the
             result of the step before it
FINITENESS   always stops after a finite number of steps
INPUT        the algorithm receives some input
OUTPUT       the algorithm produces some output

Writing an algorithm is considered the first step to programming — if it's correct, the program built from it will run correctly every single time.

4.4 Representation of Algorithms

Two common methods — a flowchart shows the logic visually; pseudocode shows it as structured English.

4.4.1 Flowchart symbols

Table 4.1
Oval / Rounded rect   START / END ("Terminator")
Rectangle             PROCESS -- an action or single step
Diamond               DECISION -- yes/no, true/false branching
Parallelogram         INPUT / OUTPUT (data symbol)
Arrow                 flow of control between shapes

4.4.2 Pseudocode

A non-formal, "not real code" description intended for HUMANS to read — never executed directly. No fixed standard, but common keywords:

Common pseudocode keywords
INPUT   COMPUTE   PRINT   INCREMENT   DECREMENT
IF/ELSE   WHILE   TRUE/FALSE
Example 4.4 — area & perimeter of a rectangle
INPUT length
INPUT breadth
COMPUTE Area = length * breadth
PRINT Area
COMPUTE Perim = 2 * (length + breadth)
PRINT Perim

4.5 Flow of Control

Events in an algorithm can flow three ways:

4.5.1 Sequence

Statements execute one after another, in order — the simplest case, as in the rectangle example above.

4.5.2 Selection

IF / IF-ELSE syntax
IF <condition> THEN
    steps when condition is true
OTHERWISE (ELSE)
    steps when condition is false
Example 4.6 — multiple conditions (chained IF/ELSE IF)
INPUT Age
IF Age < 13 THEN
    PRINT "Child"
ELSE IF Age < 20 THEN
    PRINT "Teenager"
ELSE
    PRINT "Adult"

4.5.3 Repetition (loop / iteration)

Executing statements repeatedly until a condition is satisfied. Two patterns:

Example 4.8 — KNOWN repetition count (a counter)
Step 1: SET count = 0, sum = 0
Step 2: WHILE count < 5, REPEAT steps 3 to 5
Step 3:   INPUT a number to num
Step 4:   sum = sum + num
Step 5:   count = count + 1
Step 6: COMPUTE average = sum/5
Step 7: PRINT average
Example 4.9 — UNKNOWN repetition count (sentinel-controlled WHILE)
Step 1: SET count = 0, sum = 0
Step 2: INPUT num
Step 3: WHILE num is not equal to 0, REPEAT steps 4 to 6
Step 4:   sum = sum + num
Step 5:   count = count + 1
Step 6:   INPUT num
Step 7: COMPUTE average = sum/count
Step 8: PRINT average
Why INPUT num appears twice in Example 4.9

Once BEFORE the loop (to have something to test on the very first WHILE check), and once INSIDE the loop (to get the next value before the condition is re-checked) — a classic "priming read" pattern.

4.6 Verifying Algorithms

A faulty algorithm produces faulty software — critical in banking or medical systems. Verification means taking a dry run: picking an input, manually stepping through every line, and checking the output is correct.

Worked bug — adding two times (hh:mm)
-- First draft:
hh_total = hh1 + hh2
mm_total = mm1 + mm2
PRINT T_total as hh_total, mm_total

-- Test 1: T1=5h20m, T2=7h30m -> 12h50m   (looks fine)
-- Test 2: T1=4h50m, T2=2h20m -> 6h70m   (WRONG -- not how we measure time!)

-- Fix: carry the overflow
IF (mm_total >= 60) THEN
    hh_total = hh_total + 1
    mm_total = mm_total - 60
-- Re-test 2: now correctly gives 7h10m

This demonstrates why testing only "nice" inputs isn't enough — the edge case (minutes summing past 60) is exactly what exposed the bug. Fixing it in the algorithm is far cheaper than fixing it after the software ships.

4.7 Comparison of Algorithm

More than one algorithm can solve the same problem — which to pick depends on efficiency. The textbook's running example: checking if a number is prime.

Four approaches to primality testing, from slowest to fastest
(i)   Check every divisor from 2 up to (dividend - 1)       -- SLOWEST
(ii)  Check only up to HALF the dividend (no factor exceeds it)
(iii) Check only up to the SQUARE ROOT of the dividend       -- FASTEST of these
(iv)  Check divisibility only against a PRE-STORED prime list
      (fewer calculations, but costs extra MEMORY to store the list)
Two axes for comparing algorithms
TIME COMPLEXITY    how much processing time the algorithm needs
SPACE COMPLEXITY   how much memory the algorithm needs

Method (iv) trades lower time complexity for higher space complexity --
there's often a direct trade-off between the two.

4.8–4.9 Coding and Decomposition

Once an algorithm is finalised, it's translated into a high-level language following that language's syntax (rules governing spelling, word order, punctuation). High-level code (source code) is portable across machine types, unlike low-level/machine code.

Choosing a language depends on the platform

Desktop/mobile apps target a specific OS and hardware; web apps run in any browser and may lean on cloud resources; embedded systems (digital watches, traffic signals, medical equipment) often need specialised tools or even assembly language.

Decomposition is "divide and conquer": breaking a complex problem (like the railway reservation system from 4.1 — trains, reservations, staff/security, billing, food service) into independent sub-problems that can be solved separately — even by different teams — then integrated, tested, and combined into the full solution.

8. Exercise (from the textbook — representative subset)

NCERT Exercise, Chapter 4

Work through these on paper

  1. Write pseudocode that reads two numbers, divides one by the other, and displays the quotient.
  2. Two friends flip a coin 5 times; first to win 3 flips wins a cake (1 = player 1 wins the flip, 2 = player 2). Design an algorithm to determine the winner.
  3. Write pseudocode to print all multiples of 5 between 10 and 25 (inclusive).
  4. Write pseudocode to print a bill from price and quantity, including "Bill GST" = bill + 5% tax.
  5. Write an algorithm to find the greatest of two numbers entered by the user.
  6. Write an algorithm: if the entered number is 5–15 print GREEN, 15–25 print BLUE, 25–35 print ORANGE, otherwise print "ALL COLOURS ARE BEAUTIFUL".
  7. Write an algorithm to display a water bill: first 100 units @ ₹5/unit, next 150 @ ₹10/unit, beyond 250 @ ₹20/unit, plus a flat ₹75 meter charge.
  8. What are conditionals? When are they required in a program?
  9. Write a pseudocode to calculate the factorial of a number (5! = 5×4×3×2×1).
  10. Draw a flowchart to check whether a number is an Armstrong number (e.g. 371 = 3³+7³+1³).
  11. Verify and correct this algorithm for (5, 9, 47, 99, 100, 200):
    Classify_Numbers_Algo
    INPUT Number
IF Number < 9
    "Single Digit"
Else If Number < 99
    "Double Digit"
Else
    "Big"
  12. On what values does this algorithm fail, and how would you improve it?
    Accept_1to100_Algo
    INPUT Number
IF (0<= Number) AND (Number <= 100)
    ACCEPT
Else
    REJECT
